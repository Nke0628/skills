# Diagnosing Bugs

手強いバグのための規律。フェーズを飛ばすのは明示的な正当な理由があるときだけにする。

コードベースを探索するときは、`CONTEXT.md`が存在すればそれを読み、関係するモジュールの明確なメンタルモデルを得る。触れる領域のADRも確認する。

## 伏せ字にする

このスキルでは、コマンド、出力、取得したアーティファクトを見せることになる。**まず秘密情報はすべて伏せ字にする**: その場所に`<REDACTED>`と書く。ループは環境変数に対して組み立て、認証情報は表示するものではなく環境の中にとどめる。取得したアーティファクトには認証ヘッダーが含まれる。シグナルを含む行だけを引用する。

伏せ字にした出力ではバグの診断に不十分な場合は、その旨を伝えてユーザーに尋ねる。

## フェーズ1: フィードバックループを構築する

**これがこのスキルの核心だ。** それ以外はすべて機械的な作業になる。このバグに対する**タイトな**成功/失敗シグナル(この特定のバグでredになるもの)があれば、原因は見つかる。二分探索、仮説検証、計装はすべてそれを消費するだけだ。それがなければ、コードをどれだけ眺めても救われない。

ここに不釣り合いなほどの労力をかける。**積極的に、創造的に。決してあきらめない。**

### 構築する方法(おおよそこの順序で)

1. **失敗するテスト**を、バグに届くどのシームでもよいので作る: ユニット、統合、e2e。
2. 動作中の開発サーバーに対する**curl / HTTPスクリプト**。
3. フィクスチャ入力を使った**CLI呼び出し**で、標準出力を既知の正しいスナップショットと比較する。
4. UIを操作し、DOM/コンソール/ネットワークに対してアサートする**ヘッドレスブラウザスクリプト**(Playwright / Puppeteer)。
5. **取得したトレースをリプレイする。** 実際のネットワークリクエスト/ペイロード/イベントログをディスクに保存し、コードパスを単独でリプレイする。
6. **使い捨てのハーネス。** システムの最小限のサブセット(1つのサービス、モック化した依存関係)を立ち上げ、単一の関数呼び出しでバグのコードパスを実行させる。
7. **プロパティ/ファズループ。** バグが「たまに出力が間違う」というものなら、1000件のランダム入力を実行して失敗パターンを探す。
8. **二分探索ハーネス。** バグが2つの既知の状態(コミット、データセット、バージョン)の間で発生した場合、「状態Xで起動、確認、繰り返す」を自動化し、`git bisect run`できるようにする。
9. **差分ループ。** 同じ入力を旧バージョンと新バージョン(または2つの設定)の両方に通し、出力を比較する。
10. **HITL(人間参加型)bashスクリプト。** 最後の手段。人間がクリックする必要がある場合でも、`scripts/hitl-loop.template.sh`で*その人間を*動かすことで、ループを構造化された状態に保つ。取得された出力はあなたにフィードバックされる。

正しいフィードバックループを構築できれば、バグは9割解決したようなものだ。

### ループを締める

ループを製品として扱う。ひとたび*ある*ループができたら、それを**締める**:

- もっと速くできないか?(セットアップをキャッシュする、無関係な初期化をスキップする、テストの範囲を狭める。)
- シグナルをもっと鋭くできないか?(「クラッシュしなかった」ではなく、具体的な症状に対してアサートする。)
- もっと決定的にできないか?(時刻を固定する、乱数のシードを固定する、ファイルシステムを隔離する、ネットワークを凍結する。)

30秒かかるフレークなループは、ループがないのとほとんど変わらない。2秒の決定的なループはタイトで、デバッグの超能力になる。

### 非決定的なバグ

目指すのはクリーンな再現ではなく、**より高い再現率**だ。トリガーを100回ループさせる、並列化する、負荷をかける、タイミングの窓を狭める、sleepを注入する。50%のフレークバグはデバッグ可能だが、1%は不可能だ。デバッグできる水準まで再現率を上げ続ける。

### 本当にループを構築できない場合

立ち止まり、その旨をはっきり伝える。試したことを列挙する。ユーザーに以下を求める: (a) それを再現できる環境へのアクセス、(b) 伏せ字にした取得アーティファクト(HARファイル、ログダンプ、コアダンプ、タイムスタンプ付きの画面録画)、または(c) 一時的な本番計装を追加する許可。ループなしで仮説立てに進んでは**いけない**。

### 完了基準: redになるタイトなループ

フェーズ1が完了するのは、ループが**タイト**かつ**red化可能**なとき、つまり**1つのコマンド**(スクリプトのパス、テストの呼び出し、curl)を名指しでき、それを**すでに少なくとも一度実行済み**(その呼び出しと出力を、伏せ字にして示す)であり、かつ以下を満たすときだ:

- [ ] **Red化可能**: 実際のバグのコードパスを駆動し、**ユーザーの正確な症状**に対してアサートしており、このバグでredになり、修正後にgreenになりうる。「エラーなく動く」ではなく、_この特定のバグを_捕まえられなければならない。
- [ ] **決定的**: 毎回同じ結果になる(フレークなバグの場合は、上記の通り固定された高い再現率であること)。
- [ ] **速い**: 分単位ではなく秒単位。
- [ ] **エージェントが実行可能**: 無人で実行できる。人間が関わるのは`scripts/hitl-loop.template.sh`経由のみ。

このコマンドが存在する前にコードを読んで理論を立てようとしていることに気づいたら、**立ち止まる: 仮説にいきなり飛びつくことこそ、このスキルが防ごうとしている失敗そのものだ。** red化可能なコマンドがなければ、フェーズ2はない。

## フェーズ2: 再現+最小化

ループを実行する。バグが現れてredになるのを見る。

確認する:

- [ ] ループが、**ユーザーが**説明した失敗モードを生み出しているか。たまたま近くにある別の失敗ではないか。バグを取り違えれば、修正も取り違える。
- [ ] その失敗は複数回の実行にわたって再現可能か(あるいは、非決定的なバグの場合、デバッグに足る十分な高さの率で再現可能か)。
- [ ] 正確な症状(エラーメッセージ、誤った出力、遅いタイミング)を取得済みで、後のフェーズで修正が実際にそれに対処しているか検証できるか。

### 最小化する

redになったら、**それでもredになる最小のシナリオ**まで再現手順を縮める。入力、呼び出し元、設定、データ、手順を**一度に1つずつ**削り、削るたびにループを再実行し、失敗にとって不可欠なものだけを残す。

なぜそうするか: 最小の再現手順はフェーズ3の仮説空間を縮める(疑うべき可動部分が少なくなる)し、フェーズ5でそのままクリーンなリグレッションテストになる。

**残っている要素すべてが不可欠である**状態になったら完了だ: そのうちどれか1つでも取り除くとループがgreenになる。

再現**かつ**最小化するまで先へ進まない。

## フェーズ3: 仮説を立てる

どれか1つでもテストする前に、**3〜5個のランク付けされた仮説**を生成する。単一の仮説を生成すると、最初にもっともらしく見えたアイデアに固着してしまう。

各仮説は**反証可能**でなければならない: それが立てる予測を明記する。

> 形式: 「もし<X>が原因なら、<Yを変えること>でバグが消える/<Zを変えること>でバグが悪化するはずだ。」

その予測を述べられないなら、その仮説はただの勘だ。捨てるか、鋭くする。

**テストする前に、ランク付けした一覧をユーザーに見せる。** ユーザーは即座に順位を入れ替えるドメイン知識を持っていることが多い(「その3番目のやつは、ちょうどデプロイしたところだ」)。あるいはすでに除外済みの仮説を知っている。安価なチェックポイントで、大きな時間の節約になる。ユーザーが離席中ならブロックせず、自分のランク付けのまま進める。

## フェーズ4: 計装する

各プローブはフェーズ3の特定の予測に対応していなければならない。**一度に1つの変数だけを変える。**

ツールの優先順位:

1. 環境がサポートしていれば**デバッガ/REPLでの調査**。1つのブレークポイントは10個のログに勝る。
2. 仮説を区別する境界での**的を絞ったログ**。
3. 「全部ログしてgrepする」は絶対にしない。

**すべてのデバッグログに固有のプレフィックスをタグ付けする**(例: `[DEBUG-a4f2]`)。最後のクリーンアップが1回のgrepで済むようになる。タグなしのログは生き残り、タグ付きのログは消える。

**パフォーマンス分岐。** パフォーマンスリグレッションの場合、ログはたいてい役に立たない。代わりに: ベースラインの測定値を確立し(タイミングハーネス、`performance.now()`、プロファイラ、クエリプラン)、その後二分探索する。先に測定し、後で直す。

## フェーズ5: 修正+リグレッションテスト

修正の**前に**リグレッションテストを書く。ただし、それに**正しいシーム**がある場合に限る。

正しいシームとは、テストが呼び出し箇所で実際に起きている**本物のバグパターン**を実行するものだ。利用可能なシームが浅すぎる場合(バグが複数の呼び出し元を必要とするのに単一呼び出し元のテストしかない、バグを引き起こした連鎖を再現できないユニットテストなど)、そこでのリグレッションテストは誤った安心感を与えるだけだ。

**正しいシームが存在しないなら、それ自体が発見だ。** それを記録する。コードベースのアーキテクチャがこのバグを封じ込めることを妨げている。次のフェーズのためにこれをフラグ立てする。

正しいシームが存在する場合:

1. 最小化した再現手順を、そのシームでの失敗するテストに変える。
2. それが失敗するのを確認する。
3. 修正を適用する。
4. それが成功するのを確認する。
5. 元の(最小化していない)シナリオに対して、フェーズ1のフィードバックループを再実行する。

## フェーズ6: クリーンアップ

完了を宣言する前に必須:

- [ ] 元の再現手順がもう再現しない(フェーズ1のループを再実行)
- [ ] リグレッションテストが通る(またはシームがない旨が文書化されている)
- [ ] すべての`[DEBUG-...]`計装が削除されている(プレフィックスを`grep`)
- [ ] 使い捨てのプロトタイプが削除されている(または明確にデバッグ用と分かる場所に移されている)
