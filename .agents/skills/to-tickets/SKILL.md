# To Tickets

プラン・スペック・会話を一連の**チケット**に分解する。トレーサーバレット式の垂直スライスであり、各チケットは自分を**ブロック**しているチケットを宣言する。

イシュートラッカーとトリアージのラベル語彙は、あなたに事前に提供されているはずだ。提供されていなければ、ユーザーに `/setup-matt-pocock-skills` を実行するよう伝える。

## プロセス

### 1. コンテキストを集める

会話の文脈にすでにあるものから作業する。ユーザーが引数として参照（スペックのパス、イシュー番号、URL）を渡した場合は、それを取得し、本文とコメントを全て読む。

### 2. コードベースを探索する（任意）

まだコードベースを探索していなければ、コードの現状を理解するために探索する。チケットのタイトルと説明にはプロジェクトのドメイン用語集の語彙を使い、触れる領域のADRを尊重する。

実装を容易にするために、コードをプリファクタリングできる機会を探す。「変更を容易にしてから、容易な変更を行う」。

### 3. 垂直スライスを起草する

作業を**トレーサーバレット**チケットに分解する。

<vertical-slice-rules>

- 各スライスは、あらゆるレイヤー（スキーマ、API、UI、テスト）を貫く狭くも完全な経路を切り出す: 垂直であり、1つのレイヤーの水平スライスでは決してない
- 完成したスライスは単独でデモ可能または検証可能である
- 各スライスは、単一の新規コンテキストウィンドウに収まるサイズにする
- プリファクタリングがあれば、最初に行うべきである

</vertical-slice-rules>

各チケットに**ブロッキングエッジ**（それが着手できるようになる前に完了していなければならない他のチケット）を与える。ブロッカーがないチケットはすぐに着手できる。

**大規模リファクタリングは垂直スライス化の例外である。** **大規模リファクタリング**とは、列名の変更や共有シンボルの型変更のような1つの機械的な変更で、その**爆発半径**がコードベース全体に広がり、1回の編集で何千もの呼び出し箇所が一斉に壊れてしまい、どの垂直スライスもグリーンで着地できないものを指す。これを無理にトレーサーバレットに押し込まず、**expand-contract（拡張-収縮）**として順序立てる。まず拡張: 何も壊さないよう、旧形式のそばに新形式を追加する。次に呼び出し箇所を爆発半径に応じたサイズのバッチ（パッケージ単位、ディレクトリ単位）で移行する。各バッチは独自のチケットとし、拡張チケットにブロックされるようにする。旧形式がまだ存在するため、バッチからバッチへCIはグリーンのまま保たれる。最後に収縮: 呼び出し元が残っていないことを確認したうえで旧形式を削除する。このチケットは全ての移行バッチにブロックされる。バッチ単体でもグリーンを保てない場合でも、順序は維持しつつ、それらに統合ブランチを共有させ、そのブランチ全体を最終的な統合・検証チケットがブロックする形にする。グリーンが保証されるのはそこだけになる。

### 4. ユーザーに確認する

提案する分解を番号付きリストとして提示する。各チケットについて以下を示す。

- **タイトル**: 短い説明的な名前
- **ブロック元**: 先に完了していなければならない他のチケット（あれば）
- **提供するもの**: このチケットによってエンドツーエンドで動くようになる振る舞い

ユーザーに尋ねる。

- 粒度は適切か?（粗すぎる／細かすぎる）
- ブロッキングエッジは正しいか: 各チケットは、本当にそれをゲートしているチケットだけに依存しているか?
- どれかを統合または分割すべきか?

ユーザーが分解を承認するまで繰り返す。

### 5. チケットを設定済みのトラッカーに公開する

承認されたチケットを公開する。**方法**は `/setup-matt-pocock-skills` が設定したトラッカーによって異なる。チケット自体は同じだが、ブロッキングエッジの形だけが変わる。

- **ローカルファイル** → `.scratch/<feature-slug>/issues/<NN>-<slug>.md` の下に、チケット1件につき1ファイルを書き出す。依存関係の順（ブロッカーが先）で `01` から番号付けする。各ファイルの「Blocked by」には依存する番号／タイトルを列挙する。以下のチケットごとのファイルテンプレートを使う: 1チケット1ファイルであり、複数を1つの結合ファイルにまとめてはならない。
- **実際のイシュートラッカー（GitHub、Linear など）** → 依存関係の順（ブロッカーが先）でチケットごとに1イシューを公開し、各チケットのブロッキングエッジが実際のIDを参照できるようにする。プラットフォームにネイティブなブロッキング／サブイシュー関係があればそれを使い、なければ各チケットの「Blocked by」にブロックしているイシューを設定する。指示がない限り `ready-for-agent` トリアージラベルを適用する。これらのチケットは構造上、エージェントがそのまま拾える状態になっている。

**フロンティア**（ブロッカーが全て完了しているチケット）に取り組む。単純な線形チェーンの場合、それは上から下への順番を意味する。

親イシューをクローズしたり変更したりしないこと。

<local-ticket-template>

# <NN>: <チケットタイトル>

**構築するもの:** このチケットによってエンドツーエンドで動くようになる振る舞い。ユーザーの視点から見たものであり、レイヤーごとの実装リストではない。

**ブロック元:** このチケットをゲートしているチケットの番号／タイトル、または「None (can start immediately)」。

**ステータス:** ready-for-agent

- [ ] 受け入れ基準2

</local-ticket-template>

<issue-template>

## 構築するもの

このチケットによってエンドツーエンドで動くようになる振る舞い。ユーザーの視点から見たものであり、レイヤーごとの実装ではない。

## 受け入れ基準

- [ ] 基準2

- 各ブロッキングチケットへの参照、または「None (can start immediately)」。

</issue-template>

どちらの形式でも、具体的なファイルパスやコードスニペットは避ける。すぐに古くなるためだ。例外: プロトタイプが、散文よりも正確に決定をエンコードするスニペット（状態マシン、リデューサー、スキーマ、型の形）を生み出した場合は、それをインラインで含め、プロトタイプ由来であることを簡潔に注記する。動くデモではなく、決定に富む部分だけ、重要な部分だけに絞り込む。
