`HEAD`とユーザーが指定した固定点との間の差分を2軸でレビューする:

- **Standards**: コードはこのリポジトリで文書化されたコーディング標準に準拠しているか?
- **Spec**: コードは元になったissue/仕様書を忠実に実装しているか?

両方の軸は**並列サブエージェント**として実行され、互いのコンテキストを汚染しない。その後このスキルが両者の結果を集約する。

issueトラッカーはすでにあなたに与えられているはずだ。`docs/agents/issue-tracker.md`が存在しない場合は、`/setup-matt-pocock-skills`を実行するようユーザーに伝える。

## プロセス

### 1. 固定点を定める

ユーザーが言ったものが固定点になる(コミットSHA、ブランチ名、タグ、`main`、`HEAD~5`など)。指定がなければ尋ねる。

差分コマンドを一度控える: `git diff <fixed-point>...HEAD`(三点、つまりマージベースとの比較)。コミット一覧も`git log <fixed-point>..HEAD --oneline`で記録する。

先へ進む前に、固定点が解決できること(`git rev-parse <fixed-point>`)と差分が空でないことを確認する。不正な参照や空の差分は、2つの並列サブエージェントの中ではなくここで失敗させるべきだ。

### 2. 仕様の出所を特定する

元になった仕様書を、次の順序で探す:

1. コミットメッセージ内のissue参照(`#123`、`Closes #45`、GitLabの`!67`など)。`docs/agents/issue-tracker.md`のワークフロー経由で取得する。
2. ユーザーが引数として渡したパス。
3. ブランチ名や機能名に一致する、`docs/`、`specs/`、`.scratch/`配下の仕様ファイル。
4. 何も見つからなければ、仕様書がどこにあるかユーザーに尋ねる。ないと言われたら、**Spec**サブエージェントはスキップし、「利用可能な仕様書なし」と報告する。

### 3. 標準の出所を特定する

`CODING_STANDARDS.md`や`CONTRIBUTING.md`など、コードの書き方を文書化しているリポジトリ内のあらゆるもの。

リポジトリが文書化しているものに加えて、Standards軸は常に以下の**スメルのベースライン**を持つ。これはFowlerのコードスメル(『リファクタリング』第3章)の固定セットで、リポジトリが何も文書化していない場合でも適用される。これを縛る2つのルール:

- **リポジトリの記述が優先する。** 文書化されたリポジトリの標準は常に勝つ。それがベースラインの指摘するものを推奨している場合は、そのスメルの指摘を抑える。
- **常に判断の問題である。** 各スメルはラベル付けされたヒューリスティック("possible Feature Envy"のような)であり、決してハードな違反ではない。ここにある他の標準と同様、すでにツールが強制しているものはスキップする。

各スメルは*それが何か* → *どう直すか*の順で読む。これを差分と照らし合わせる:

- **Mysterious Name(謎の名前)**: 何をするか、何を保持するかを名前が明かさない関数・変数・型。→ 名前を変える。誠実な名前が見つからないなら、設計自体が曖昧である。
- **Duplicated Code(重複コード)**: 同じロジックの形が変更内の複数のハンクやファイルに現れる。→ 共通の形を抽出し、両方から呼ぶ。
- **Feature Envy(機能の横恋慕)**: 自分自身のデータより他のオブジェクトのデータに多くアクセスするメソッド。→ そのメソッドを、恋慕しているデータの側へ移す。
- **Data Clumps(データの群れ)**: 同じ数個のフィールドやパラメータがいつも一緒に移動している(生まれたがっている型)。→ それらを1つの型にまとめ、それを渡す。
- **Primitive Obsession(基本型への執着)**: 独自の型に値するドメイン概念の代わりにプリミティブや文字列が使われている。→ その概念に小さな独自の型を与える。
- **Repeated Switches(繰り返されるswitch)**: 同じ型に対する同じ`switch`/`if`のカスケードが変更全体に繰り返し現れる。→ ポリモーフィズムに置き換えるか、両方の箇所で共有する1つのマップにする。
- **Shotgun Surgery(散弾銃手術)**: 1つの論理的な変更が、差分内の多くのファイルにまたがる散発的な編集を強いる。→ 変化するものを1つのモジュールにまとめる。
- **Divergent Change(発散的変更)**: 1つのファイルやモジュールが複数の無関係な理由で編集されている。→ 各モジュールが1つの理由でだけ変化するように分割する。
- **Speculative Generality(投機的一般化)**: 仕様が求めていないニーズのために追加された抽象化、パラメータ、フック。→ 削除する。実際のニーズが現れるまでインライン化して戻す。
- **Message Chains(メッセージの連鎖)**: 呼び出し側が依存すべきでない長い`a.b().c().d()`のナビゲーション。→ その辿り方を最初のオブジェクトの1つのメソッドの裏に隠す。
- **Middle Man(仲介者)**: ほとんど単に委譲するだけのクラスや関数。→ それを削り、本当の対象を直接呼ぶ。
- **Refused Bequest(拒否された遺産)**: 継承したものの大半を無視またはオーバーライドするサブクラスや実装。→ 継承をやめ、コンポジションを使う。

### 4. 両方のサブエージェントを並列で起動する

**Standardsサブエージェントのプロンプト**には以下を含める:

- 完全な差分コマンドとコミット一覧。
- ステップ3で見つけた標準の出所ファイルの一覧、**加えてステップ3のスメルのベースラインを全文貼り付けたもの**(サブエージェントにはそれ以外のアクセス手段がない)。
- 依頼内容: 「関係する各ファイル/ハンクごとに、(a) 差分が文書化された標準に違反している箇所すべてを報告する: 標準を引用する(ファイル + 規則)。(b) 気づいたベースラインのスメルを報告する: 名前を挙げ、該当ハンクを引用する。ハードな違反と判断の問題を区別すること: 文書化された標準への違反はハードな場合があるが、ベースラインのスメルは常に判断の問題であり、文書化されたリポジトリの標準はベースラインに優先する。ツールが強制しているものはスキップする。400語以内。」

**Specサブエージェントのプロンプト**には以下を含める:

- 差分コマンドとコミット一覧。
- 仕様書のパスまたは取得済みの内容。
- 依頼内容: 「報告する内容: (a) 仕様書が求めていたのに、欠けている、または部分的にしか実装されていない要件。(b) 求められていなかったのに差分に含まれる振る舞い(スコープクリープ)。(c) 実装されているように見えるが、実装が誤って見える要件。各指摘について仕様書の該当行を引用する。400語以内。」

仕様書がなければ、Specサブエージェントはスキップし、最終レポートにその旨を記す。

### 5. 集約する

2つのレポートを`## Standards`と`## Spec`の見出しの下に、そのまま、または軽く整えて提示する。2つの軸はわざと分離してあるので(「なぜ2軸か」を参照)、指摘事項を**統合したり、順位を付け直したりしない**。

最後に1行の要約を添える: 軸ごとの指摘の総数と、**各軸内での**最悪の問題(あれば)。軸をまたいだ単一の勝者は選ばない。それはこの分離が防ごうとしている順位付け直しそのものだから。

## なぜ2軸か

変更は片方の軸には合格し、もう片方には不合格になることがある:

- あらゆる標準に従っているが、間違ったものを実装しているコード → **Standards合格、Spec不合格。**
- issueが求めた通りに正確に動くが、プロジェクトの規約を破っているコード → **Spec合格、Standards不合格。**

別々に報告することで、片方の軸がもう片方を覆い隠してしまうのを防ぐ。
