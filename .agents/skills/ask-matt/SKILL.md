# Ask Matt

すべてのスキルを覚えていられるわけではないので、尋ねればいい。

**フロー**とはスキルを通る一本の道筋だ。ほとんどの道筋は1本の**メインフロー**に沿って進み、2つの**オンランプ**がそこに合流する。それ以外はスタンドアロンか、その下を走る語彙レイヤーだ。

## メインフロー: アイデア → 出荷

ほとんどの作業が辿るルート。アイデアがあって、それを形にしたい場合。

1. **`/grill-with-docs`**がインタビューによってアイデアを研ぎ澄ます。**作業ディレクトリ内で作業している**ときは常にここから始める。これはステートフルで、学んだことを`CONTEXT.md`とADRに保持する。(作業ディレクトリがない? 代わりに`/grill-me`を使う。スタンドアロンの項で扱う。どちらも同じ`/grilling`プリミティブを実行するが、`grill-with-docs`は記録を残す方なので、それを残せるリポジトリがあるなら常にこちらの方が優れている。)
2. **分岐: すべての疑問を会話だけで解決できるか?** ある疑問がランタイムで動く答えを必要とする場合(状態、ビジネスロジック、実際に見てみないとわからないUI)は、プロトタイプへ寄り道する。この寄り道は両方向とも**`/handoff`**で橋渡しする(プロトタイプは独自のディレクトリに存在し、それはまさに`/handoff`の出番だ。「フェーズ境界」を参照):
   - **`/handoff`**で外へ出て、そのファイルを対象に新しいセッションを開く、
   - **`/prototype`**で使い捨てコードによってその疑問に答える、
   - 学んだことを**`/handoff`**で元のアイデアのスレッドに戻し、そこから参照する。
3. **分岐: これは複数セッションにまたがるビルドか?**
   - **はい** → **`/to-spec`**(スレッドを仕様書に変換する)、続いて**`/to-tickets`**でそれをトレーサーバレット式のチケットに分割し、それぞれが自分の**ブロッキングエッジ**を宣言する。ローカルのトラッカーでは、これは`.scratch/<feature>/issues/`配下のチケット1件につき1ファイルであり、ブロッカーの多いものから手作業で片付けていく。実際のトラッカーでは、そのエッジがネイティブのブロッキングリンクになるため、ブロッカーが片付いたチケットはいつでも取りかかれる。チケットごとに**`/implement`**を起動し、**1件ごとにコンテキストを`/clear`する**。各チケットは自己完結しているので、最後のチケットのコンテキストは使い捨てにできる。
   - **いいえ** → その場で同じコンテキストウィンドウのまま**`/implement`**。

   いずれの場合も、**`/implement`**は内部で**`/tdd`**を駆動して(一度に1つのred-green単位で)各issueを構築し、コミット前に**`/code-review`**(差分に対するStandards + Specの二軸レビュー)を実行して締めくくる。仕様書全体なしに具体的な振る舞いをテストファーストで組みたいだけのときは**`/tdd`**単体を、ブランチやPRを固定点と照らして単体でレビューしたいときは**`/code-review`**単体を使う。

### コンテキストの衛生管理

手順1〜3は**ひとつの途切れないコンテキストウィンドウ**の中で行う(`/to-tickets`が終わるまでコンパクトもクリアもしない)。そうすることで、grilling、仕様書、チケットがすべて同じ思考の上に積み上がる。その後、各`/implement`はチケットから出発してまっさらに始まる。

これを制約するのは**[スマートゾーン](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**だ。モデルが依然として鋭く推論できる範囲(最先端モデルで約15万トークン)のこと。`/to-tickets`の前にセッションがそこに近づいてきたら、劣化した状態で押し切らない。最寄りのフェーズ境界で`/compact`し、続ける(「フェーズ境界」を参照)。

## オンランプ

作業を生み出す出発点で、その後メインフローに合流する。

- **バグと要望が積み上がっている** → **`/triage`**。issueをトリアージの役割に沿って動かし、エージェントがすぐ着手できるissueを生成する。それを後で**`/implement`**が拾う。

  トリアージは**自分が作っていない**issue専用だ。バグ報告、届いた機能要望、生のまま到着したものすべて。`/to-tickets`が生成したチケットはすでにエージェント対応済みなので、**トリアージしない**。

- **何かが壊れている** → **`/diagnosing-bugs`**。手強いバグ向けだ。一目見ただけでは解けないバグ、間欠的に起きるフレーク、既知の良好な2つの状態の間に紛れ込んだリグレッション。**タイトなフィードバックループ**(この特定のバグですでにredになる1つのコマンド)を確保するまでは理論化を拒否し、その後リグレッションテストで固定する。事後検証は、真の発見が「このバグを封じ込める良いシームがない」ことだった場合、**`/improve-codebase-architecture`**に引き継ぐ。

- **巨大で霧のかかった取り組み: グリーンフィールドプロジェクトや、1セッションには大きすぎる巨大な機能構築** → **`/wayfinder`**。ここにあるフローの中で最も認知負荷が高いものだ。ここから目的地までの道筋がまだ見えていないとき、issueトラッカー上に**決定チケット**の**共有マップ**を描き、それを1つずつ解決していき、霧が晴れて道が見えるまで**成果物ではなく決定**を生み出す。**`/grill-with-docs`**が1セッションに収まるアイデアを研ぎ澄ますのに対し、wayfinderは収まらないアイデアのためのものであり、より遅く、より濃密だ。だからそのためだけに取っておき、程よく絞られた機能には決して使わない。

  霧が晴れたら、**それは引き継ぐだけで、構築はしない**。メインフローには**`/to-spec`**で合流し、マップが持つ連結した決定群をひとつの構築可能なプランへと折りたたむ。その後は通常通り`/to-tickets`と`/implement`。マップを直接`/implement`にループさせると、この折りたたみを飛ばして連結された詳細を捨ててしまうことになるので、その取り組みが実際には小さかったと判明したときだけ`/implement`に直行する。

## コードベースの健全性

機能開発ではなく、単なる保守。

- **`/improve-codebase-architecture`**は、コードベースをエージェントが操作しやすい状態に保つための空き時間があるときにいつでも実行する。**深化の機会**を洗い出し、その1つを選ぶと_アイデアが生まれる_。それをメインフローの`/grill-with-docs`に持ち込める。それは候補を見つける調査であり、**`/codebase-design`**(下記)は選んだ候補を設計する作業台だ。

## 下を流れる語彙

他のスキルの下を流れる、モデルが自発的に呼び出す2つのリファレンスで、それぞれがその語彙の唯一の正典だ。プロセスではなく**言葉**そのものが問題になっているときは直接それらに手を伸ばす。あるいは上記のスキル群がそれらを取り込むのに任せる。

- **`/domain-modeling`**: プロジェクトの*ドメイン*言語を研ぎ澄ます。曖昧な用語に異議を唱え、多義的な単語("account"が3つの役割を兼ねているなど)を解消し、後戻りしにくい決定をADRとして記録する。`CONTEXT.md`をきれいな用語集に保つために`/grill-with-docs`が駆動する能動的な規律そのもの。
- **`/codebase-design`**はモジュールの*形*を設計するための深いモジュールの語彙(module、interface、depth、seam、adapter、leverage、locality)だ。小さなインターフェースの裏に大量の振る舞いを持たせる。`/tdd`と`/improve-codebase-architecture`はどちらもこの語彙で話す。

## フェーズ境界

**フェーズ**とは、セッション内の作業のまとまりのことだ。grilling、実装、QAなど。2つのフェーズの**境界**では5つの選択肢があり、その間の選択はこのマップ全体の中で最も曖昧な決定だ。

- **継続**: その場にとどまる。コストなし、失うものなし。
- **`/clear`**: ここにあるものが次に何の役にも立たないとき、ウィンドウを空にする。
- **`/handoff`**は持ち運び可能なMarkdownファイルを書き出す。用途は狭く、**新しいハーネス**、**新しいディレクトリ**、**同僚**、あるいは**フェーズの途中**での副次タスクの分岐だけ。それが買っているのは可搬性だ。
- **サブエージェント**: 絞り込んだタスクを独自のウィンドウに送り、レポートを受け取る。
- **`/compact`**は現在のコンテキストを圧縮し、それを種に新しいセッションを始める。ツリーの最初の一手ではなく、その**デフォルト**、つまり一番下にある。

順序立てられたツリー(5つの問い、各分岐の背後にある理由、そしてなぜ一次情報源のコストが**継続**を最初に除外すべき選択肢にするのか)については[PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md)を読む。決定は境界で**行う**。フェーズの途中では、続けるか残りをサブエージェントに分割する。

## スタンドアロン

メインフローから完全に外れているもの。

- **`/grill-me`**: `/grill-with-docs`と同じ徹底的なインタビューだが、**ステートレス**だ。ローカルには何も保存せず、`CONTEXT.md`も構築しない。**作業ディレクトリの中にいない**とき(プラン、デザイン、文章の断片など、下にリポジトリのない何かを研ぎ澄ますとき)に使う。作業ディレクトリの中にいるなら、代わりに`/grill-with-docs`を使う。同じインタビューを実行しつつ記録を残すので、厳密にこちらの方が優れている。
- **`/grilling`**はインタビューそのもののプリミティブだ。ラウンド、フロンティア、事実を集めるのはエージェントの仕事で、決めるのはあなたの仕事。`/grill-me`と`/grill-with-docs`はそこへの2つの正式な入り口であり、`/triage`、`/wayfinder`、`/improve-codebase-architecture`はすべて内部でこれを実行する。ラッパーなしのインタビューがそのまま欲しいときだけ直接手を伸ばす。
- **`/resolving-merge-conflicts`**は進行中のマージやリベースのコンフリクトを、ハンクごとに扱う。行を選ぶのではなく、各側の一次情報源に遡った**意図**によって解決し、その後操作を完了させる。`--abort`は決して実行しない。スタンドアロンでどのフローにも属さない。すでにコンフリクトの最中にいるときに手を伸ばす。
- **`/prototype`**は1つのデザイン上の疑問に答える、小さな使い捨てのプログラムだ。この状態モデルはしっくりくるか、あるいはこのUIはどうあるべきか。使い捨てというのはコードの書き方に対する制約であって、破棄するという約束ではない。その答えは本物のコードに折り込まれ、プロトタイプ自体は`main`から分岐した`prototype/<name>`ブランチ上に**一次情報源**として保持され、実装issueから参照される。これはメインフローのステップ2にある寄り道だが、デザイン上の疑問を紙の上だけで解決しにくいときはいつでも手を伸ばしてよい。
- **`/research`**: 読み込み作業を**バックグラウンドエージェント**に委任する。**一次情報源**を突き合わせて疑問を調査し、出典付きのMarkdownファイルをリポジトリに残す。それが読んでいる間も作業を続けられる。生成されるファイルは`/grill-with-docs`によってメインフローに*持ち込む*ものだ。調査は思考を置き換えるのではなく、それに材料を与えるものだから。
- **`/to-questionnaire`**は、行き詰まっている原因が自分の頭やコードベースの中ではなく**他人の頭の中**にあるときに登場し、それを埋めてもらうためのアンケートを書く。`/grill-me`の逆だ。対象についてあなたにインタビューする代わりに、**送信先**(誰に送るのか、何を返してほしいのか)についてあなたにインタビューし、質問をそのギャップに狙い定める。返ってきたものは`/grill-with-docs`や`/to-spec`のための材料になる。
- **`/wizard`**は**人間**にしかできない手順のためのものだ。インフラのプロビジョニング、認証情報やCIシークレットの設定、不慣れなサードパーティのダッシュボードをクリックして進む作業、一度きりの移行やカットオーバー。各URLを開き、各値を取り込み、それを`.env`とGitHubシークレットに書き込む対話型のbashスクリプトを生成するので、その手順を毎回エージェントに説明し直す必要がなくなる。モデルが自発的に呼び出すので、人間にしか突破できない壁に当たった瞬間にエージェントがこれに手を伸ばす。エージェント自身でできるならそうすべきで、これは人間が本当にループの中にいる場合のためのものだ。
- **`/wait-what`**は、うまく伝わらなかったメッセージに対する是正措置だ。他のどのスキルの最中でも、会話の途中で使うと、エージェントはあなたに欠けていた文脈を添えて、たった今言ったことを`CONTEXT.md`の語彙を使い、平易な英語で言い直す。これは事後の対処法だ。`/grill-with-docs`は事前の予防策であり、早い段階で合意された共通言語こそが専門用語の氾濫をそもそも防ぐものだから。
- **`/teach`**: 現在のディレクトリをステートフルな作業スペースとして使い、複数セッションにわたって1つの概念を学ぶ。
- **`/writing-for-agents`**は、エージェントが消費する文書(スキル、AGENTS.md、参照先のドキュメント)を書くためのリファレンスだ。

## 前提条件

**`/setup-matt-pocock-skills`**: 最初のエンジニアリングフローの前に実行し、issueトラッカー、トリアージのラベル、他のスキルが前提とするドキュメント構成を設定する。カスタムのissueトラッカーにも対応する。
