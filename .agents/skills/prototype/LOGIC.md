# Logic Prototype

誰でもボタンをクリックして状態モデルを操作できる、単一の自己完結型HTMLファイル(**共有可能なデモ**)。疑問が**ビジネスロジック、状態遷移、データ形状**に関するもの、つまり紙の上では妥当に見えても実際のケースに通してみて初めて違和感が生じるような種類のものであるときに使う。

install不要な単一ファイルなので、非開発者(デザイナー、PM、ドメインエキスパート)に手渡し、彼ら自身にモデルを体感してもらえる。だからこそコードの言葉ではなく、彼らの言葉で語ること。

## この形が正しいとき

- 「この状態機械がXの後にYというエッジケースを扱えるか自信がない。」
- 「このデータモデルは実際に...というケースを表現できるのか。」
- 「書く前にAPIがどんな形になるべきか感触をつかみたい。」
- 誰かが**ボタンを押して状態の変化を見たい**あらゆる場面。

疑問が「これはどんな見た目になるべきか」であれば、この分岐は間違いだ。[UI.md](UI.md)を使うこと。

## プロセス

### 1. 疑問を明記する

コードを書く前に、どの状態モデルとどの疑問をプロトタイピングしているのかを書き出す。デモの冒頭に一段落、(単なるコメントではなく)目に見えるイントロとして。間違った疑問に答えるロジックプロトタイプは純粋な無駄なので、あとで検証できるように疑問を明示しておく。ユーザーが今それを見ていようと、あとで離席先から戻ってこようと構わないように。

### 2. ロジックを移植可能なモジュールに切り出す

実際のロジック(疑問に答える部分)を、単一の `<script>` ブロックとして、あとで実コードベースに移して使える小さな純粋モジュールとして書く。それを取り巻くページは使い捨てだが、このモジュールはそうではない。

正しい形は疑問によって決まる。

- **純粋なリデューサー**: `(state, action) => state`。アクションが離散的なイベントで、状態が単一の値であるときに適している。
- **ステートマシン**: 明示的な状態と遷移。「今どのアクションが合法か」自体が疑問の一部であるときに適している。
- **プレーンなデータ型に対する純粋関数の小さな集合**: 暗黙の現在状態がなく、単なる変換の連続であるときに適している。
- **明確なメソッド面を持つクラスまたはモジュール**: ロジックが本当に継続的な内部状態を所有しているとき。

ページに配線しやすい形ではなく、疑問に最も合う形を選ぶこと。純粋さを保つこと: DOMなし、`document`なし、ボタンハンドラがその中に手を突っ込むこともなし。ページはそれを呼び出す側であり、逆方向にデータが流れることはない。これがプロトタイプをその寿命を超えて有用にしている理由だ。疑問に答えが出れば、検証済みのリデューサー/マシン/関数群はそのまま実モジュールへと移植できる。

### 3. 共有可能なHTMLファイルを構築する

単一ファイル、プレーンなHTML/CSS/JS: フレームワークなし、バンドラーなし、サーバーなし、すべてインラインにしてダブルクリックで開き、メールで回されても壊れないようにする。誰でも開くだけで実行できるべきだ。

非開発者向けに書くこと。すべてのラベルは**ドメイン言語**で書き、コードの言葉ではない。ボタンや状態はリデューサーではなくビジネスのように読めること。何が起きているかを平易な言葉で説明する。

上から下へ、明快な階層で配置する。

1. **タイトルと一行の説明**: このデモで何を探索できるのか(ステップ1の疑問)。
2. **現在の状態**: 関連する状態全体を、読みやすいパネルとしてレンダリングする(生のJSONダンプではなくラベル付きのフィールド)。クリックのたびに再レンダリングし、変化が見えるようにする。非開発者の理解を助ける場合は、何が変わったかを明示する。
3. **自由操作ボタン**: アクションごとに一つのボタンを常に配置し、誰でも任意の順序でモデルを触れるようにする。クリックするたびにそのアクションをディスパッチし、状態を再レンダリングする。
4. **ガイド付きウォークスルー**: **シナリオ**の集合、タブごとに一つ。各タブには、そのシナリオの短い平易な説明(設定される状況と注目すべき点)と、その下にそのシナリオのための順序立てた**押すべきボタン**を置く。各ステップは実際のボタンであり、クリックするとそのアクションが実行され、次のステップに進む。ウォークスルーを開始すると既知の初期状態にリセットされ、シナリオが毎回同じように進行するようにする。

紙の上では判断しづらい、扱いにくいケースを示すシナリオを選ぶこと: ハッピーパス、厄介なエッジケース、本来禁止されているはずのことを試みるケース。

美しさを保ちつつ抑制すること: きれいなタイポグラフィ、余裕のある余白、一つのアクセントカラー。アニメーションなし、ギミックなし、状態とボタンの邪魔をするものは何も置かない。

### 4. 引き渡す

ファイルを送るか、代わりに開いてあげる。相手は都合のいいタイミングでウォークスルーをクリックしたり自由に操作したりする。興味深い瞬間は「待って、それはできないはずなのに」や「あれ、Xは違う挙動をすると思っていた」という言葉が出るときであり、それこそが_アイデア_の中にあるバグであり、それがまさに目的である。新しいアクションや新しいシナリオが欲しければ追加すること。プロトタイプは進化する。

### 5. 答えとプロトタイプを記録する

プロトタイプがその疑問に答えたら、答えを記録し、続いて[SKILL](SKILL.md)が説明する方法でプロトタイプ自体を記録する。ロジック特有の対応関係: 検証済みのリデューサー/マシン/関数群は実モジュールに移植される(決定が吸収される)。HTMLシェルは一次資料としてプロトタイプを保持する使い捨てブランチに乗せる。単一の自己完結ファイルであるため、そこでも簡単に再実行できる状態が保たれる。

## アンチパターン

- **テストを追加しない。** テストが必要になったプロトタイプは、もはやプロトタイプではない。
- **実データベースに配線しない。** 疑問が具体的に永続化に関するものでない限り、メモリ上の状態を使う。
- **一般化しない。** 「あとでXをサポートしたくなったら」はなし。プロトタイプは一つの疑問にのみ答える。
- **ロジックとページを混ぜない。** 純粋モジュールがDOM、`document`、ボタンハンドラを参照しているなら、それはもはや移植可能ではない。ページは純粋モジュールの上に乗る薄いシェルにとどめること。
- **フレームワーク、バンドラー、サーバーに頼らない。** 受け取った人がダブルクリックする単一ファイルであること。ReactアプリやdevサーバーはShareable(共有可能)という目的を損なう。
- **HTMLシェルを本番に出荷しない。** このページは手動でクリックして操作されることに最適化されている。その裏にあるロジックモジュールこそが保つ価値のある部分だ。
