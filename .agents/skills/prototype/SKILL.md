# Prototype

プロトタイプとは**疑問に答えるための使い捨てコード**である。疑問がその形を決める。

## 分岐を選ぶ

ユーザーのプロンプト、周辺のコード、あるいはユーザーが近くにいれば直接尋ねることによって、どの疑問に答えようとしているのかを特定する。

- **「このロジック/状態モデルは正しく感じられるか?」** → [LOGIC.md](LOGIC.md)。単一の共有可能なHTMLファイル(自由操作ボタンとタブ形式のガイド付きウォークスルー)を構築し、紙の上では判断しづらいケースを通してステートマシンを動かし、非開発者でも操作できるようにする。
- **「これはどのような見た目になるべきか?」** → [UI.md](UI.md)。単一のルート上に、根本的に異なる複数のUIバリエーションを生成し、URLの検索パラメータとフローティングのボトムバーで切り替えられるようにする。

この二つの分岐はまったく異なる成果物を生むため、ここを間違えるとプロトタイプ全体が無駄になる。疑問が本当に曖昧でユーザーに確認できない場合は、周辺のコードによりよく合致する方の分岐をデフォルトとして選び(バックエンドモジュールならロジック、ページやコンポーネントならUI)、その前提をプロトタイプの冒頭に明記する。

## 両方に共通するルール

1. **初日から使い捨てであり、そうと明確に示す。** プロトタイプのコードは実際に使われる場所の近く(プロトタイプ対象のモジュールやページの隣)に置き、文脈が一目でわかるようにする。ただし、気軽な読者にもそれがプロトタイプであって本番コードではないとわかるような名前をつける。使い捨てのUIルートについては、プロジェクトが既に持っているルーティング規約に従う。新しいトップレベル構造を発明しないこと。
2. **実行が些細であること。** UIプロトタイプはプロジェクトのタスクランナーの単一コマンドから起動する: `pnpm <name>`、`python <path>`、`bun <path>` など。ロジックデモはユーザーがダブルクリックするだけの単一のHTMLファイルである。いずれの場合も、起動に考える必要が一切ないこと。
3. **デフォルトでは永続化しない。** 状態はメモリ上に存在する。永続化はプロトタイプが_検証している_対象であり、依存すべきものではない。疑問が明示的にデータベースに関わる場合は、スクラッチ用DBか、「PROTOTYPE、消してよい」と明記されたローカルファイルを使う。
4. **磨き込みは省く。** テストなし、プロトタイプを_実行可能_にするために必要な範囲を超えたエラーハンドリングなし、抽象化なし。目的は素早く何かを学ぶことにある。
5. **状態を表に出す。** アクションのたびに(ロジックの場合)、あるいはバリアント切り替えのたびに(UIの場合)、関連する状態全体を出力またはレンダリングし、何が変わったかをユーザーが見られるようにする。
6. **完了したら記録する。** 検証済みの決定を実コードに取り込んだうえで、プロトタイプ自体を**一次資料**として記録する: 使い捨てブランチにコミットし(mainの外に置く)、実装issueにそのブランチへのコンテキストポインタを残す。答え(下された結論とそれが解決した疑問)もissueかコミットに記録する。mainブランチには検証済みの決定のみが残る。
