# Deepening

浅いモジュールのクラスタを、その依存関係を踏まえて安全に深化させる方法。[SKILL.md](SKILL.md)にある語彙を前提とする: **module**、**interface**、**seam**、**adapter**。

## 依存関係のカテゴリ

深化の候補を評価するときは、その依存関係を分類する。このカテゴリが、深化させたモジュールをそのシーム越しにどうテストするかを決める。

### 1. In-process(プロセス内)

純粋な計算、インメモリの状態、I/Oなし。常に深化可能: モジュールを統合し、新しいインターフェースを通して直接テストする。アダプターは不要。

### 2. Local-substitutable(ローカルで代替可能)

ローカルのテスト用代替物がある依存関係(Postgresに対するPGLite、インメモリのファイルシステムなど)。代替物が存在すれば深化可能。深化させたモジュールは、テストスイート内で動く代替物を使ってテストする。シームは内部にあり、モジュールの外部インターフェースにportは置かない。

### 3. Remote but owned(自分が所有するリモート、Ports & Adapters)

ネットワーク境界を越えた自分自身のサービス(マイクロサービス、内部API)。シームに**port**(インターフェース)を定義する。深いモジュールがロジックを所有し、トランスポートはアダプターとして注入される。テストではインメモリのアダプターを使う。本番ではHTTP/gRPC/キューのアダプターを使う。

推奨の形: 「シームにportを定義し、本番用にHTTPアダプターを、テスト用にインメモリアダプターを実装する。そうすればネットワークをまたいでデプロイされていても、ロジックは1つの深いモジュールの中に収まる。」

### 4. True external(真に外部、Mock)

自分が制御していないサードパーティサービス(Stripe、Twilioなど)。深化させたモジュールは外部依存関係を注入されたportとして受け取り、テストにはモックのアダプターを与える。

## シームの規律

- **アダプターが1つならそれは仮説的なシーム。2つならそれは本物のシームだ。** 少なくとも2つのアダプター(通常は本番用とテスト用)が正当化されない限り、portを導入しない。アダプターが1つだけのシームは単なる間接化にすぎない。
- **内部シーム vs 外部シーム。** 深いモジュールは、実装に固有で自身のテストが使う内部シームに加えて、インターフェースにある外部シームを持つことができる。テストが使うからといって、内部シームをインターフェース越しに公開しない。

## テスト戦略: 置き換える、積み上げない

- 浅いモジュールに対する古いユニットテストは、深化させたモジュールのインターフェースでのテストが存在するようになった時点で無駄になる。削除する。
- 深化させたモジュールのインターフェースで新しいテストを書く。**インターフェースがテストの表面である。**
- テストはインターフェースを通した観測可能な結果に対してアサートし、内部状態には対してアサートしない。
- テストは内部のリファクタリングを生き延びるべきだ。テストは実装ではなく振る舞いを記述しているから。実装が変わるたびにテストも変えなければならないなら、それはインターフェースの先をテストしている。
