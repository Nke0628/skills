# Test-Driven Development

TDDはred→greenのループである。このスキルは、そのループが手放したくないテストを生み出すためのリファレンスである: 良いテストとは何か、テストをどこに置くか、アンチパターン、そしてループのルール。すべてのセクションはあらゆるサイクルに適用される。ループの前と最中に参照すること。後からではない。

コードベースを探索する際は、テスト名とインターフェースの語彙がプロジェクトのドメイン言語と一致するよう`CONTEXT.md`(存在すれば)を読み、取り組む領域のADRを尊重すること。

## 良いテストとは何か

テストは実装の詳細ではなく、公開インターフェースを通して振る舞いを検証する。コードは丸ごと変わってもよいが、テストは変わるべきではない。良いテストは仕様のように読める。「user can checkout with valid cart」は、どんな機能が存在するかを正確に伝えており、内部構造を気にしないのでリファクタを生き延びる。

例については[tests.md](tests.md)を、モックのガイドラインについては[mocking.md](mocking.md)を参照。

## Seams: テストをどこに置くか

**seam**とは、内部に立ち入ることなく振る舞いを観測できる公開境界のことで、テストを行う場所である。テストはseamに置き、決して内部に対しては置かない。

**事前に合意したseamでのみテストする。** テストを書く前に、テスト対象のseamを書き出し、ユーザーと確認する。合意されていないseamでテストは書かない。すべてをテストすることはできないので、事前にseamを合意することが、テストの労力をあらゆるエッジケースではなくクリティカルパスと複雑なロジックに向けさせる方法である。

問う: 「公開インターフェースは何で、どのseamをテストすべきか?」

そのインターフェースの形そのものが問題になっている場合(モジュールがどれだけ深いか、seamがどこにあるべきか、インターフェースが何を公開すべきか)、Skillツールで「codebase-design」を呼び出して語彙を得ること。それはmodule、interface、depth、seam、adapter、leverage、localityという用語の共有ソースであり、実行するセッションではなく参照すべきリファレンスである。

## アンチパターン

- **実装結合**: 内部の協調オブジェクトをモックする、プライベートメソッドをテストする、あるいは側道(インターフェースを使う代わりにデータベースに問い合わせる)を通して検証する。兆候: 振る舞いが変わっていないのにリファクタするとテストが壊れる。
- **同語反復**: アサーションがコードと同じ方法で期待値を再計算する(`expect(add(a, b)).toBe(a + b)`、コードと同じ方法で手動で導出されたスナップショット、自分自身と等しいと主張される定数)ので、構造上必ず通ってしまい、コードと食い違うことがあり得ない。期待値は独立した信頼できる情報源から得なければならない: 既知の正しいリテラル、実例、仕様。
- **水平スライス**: すべてのテストを先に書いてから、すべての実装を書くこと。まとめて書いたテストは_想像上の_振る舞いを検証する。物事の_形_をテストしているだけで、ユーザーが目にする振る舞いをテストしていない。テストは実際の変更に鈍感になり、実装を理解する前にテスト構造にコミットしてしまう。代わりに**垂直スライス**で作業する: 1つのテスト→1つの実装→繰り返し。各テストは、直前のサイクルが教えてくれたことに応答する**トレーサー弾**である。

## ループのルール

- **greenの前にred。** まず失敗するテストを書き、それを通すのに必要な分だけコードを書く。将来のテストを先取りしたり、投機的な機能を追加したりしない。
- **一度に1スライス。** 1サイクルにつき1つのseam、1つのテスト、1つの最小限の実装。
- **リファクタリングはループの一部ではない。** それはred→green実装サイクルではなく、レビュー段階(`code-review`スキルを参照)に属する。
