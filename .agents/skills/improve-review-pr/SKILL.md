修正PR(バグ修正やレビュー後の指摘対応のPR)を分析し、なぜ元のPRのレビューでその問題が見落とされたかを突き止め、汎用的なチェックパターンに抽象化して`/code-review`のガイドラインに蓄積する。目的は、同じ種類の見落としを`/code-review`が二度としないようにすることだ。

書き込み先は`/code-review`スキルの`guidelines/team.md`(チーム固有の観点)と`guidelines/common.md`(技術を問わない観点)。インストールされている`code-review`スキルのディレクトリ(`.claude/skills/code-review/`など)を探して特定する。見つからない、または複数ある場合はユーザーに尋ねる。どちらのファイルもチーム全体のレビュー挙動に影響するため、必ず承認を得てから書き換える。

## プロセス

### 1. 修正PRを取得する

`gh pr view <PR番号> --json title,body,url`および`gh pr diff <PR番号>`で、引数に渡された修正PRのタイトル・本文・差分を取得する。引数がPR番号でなくURLなら、そこから番号を抽出する。

### 2. 元PRを特定する

修正PRの本文から、対応した元のPRへの参照を探す(`Fixes #123`、`Follow-up to #123`、本文中のPR/issueリンクなど)。見つかれば`gh pr view`と`gh pr diff`でその内容も取得する。見つからなければユーザーに尋ねる。それでも不明なら、元PRなしで手順3に進む(修正PRの差分だけから見落としパターンを推定する)。

### 3. 見落としの理由を分析する

元PRの差分と修正PRの差分を突き合わせ、次を突き止める:

- 元PRのどのコード(ファイル・ハンク)が問題を含んでいたか
- それは`/code-review`のガイドライン(`guidelines/common.md`・`guidelines/team.md`)のどちらが拾うべきものだったか
- なぜそのレビューで見落とされたのか(ガイドラインに含まれていない、チーム固有の文脈が必要、パターンが一目では気づきにくい、など)

元PRが不明な場合は、修正PRの差分自体から「何が壊れていて、何を直したか」を読み取り、同じ推論を行う。

### 4. 汎用チェックパターンに抽象化する

個別の修正を、再利用可能なチェック項目に変換する。ガイドラインの既存項目と同じく、レビュアーが差分を見て判定できる「〜になっているか」「〜していないか」の形にする。次の3つに分類する:

- **チーム固有**: チームの技術スタック・アーキテクチャ・規約・ドメインに依存する見落とし(例: 「`X`の変更時に`Y`も更新されているか」)。`team.md`に追加する。
- **汎用**: どの技術・プロジェクトにも当てはまる一般的な見落とし。`common.md`に追加する。
- **既存強化**: すでにガイドラインにある項目と本質的に同じだが、この修正PRのケースでは表現が曖昧で拾いきれなかったもの。新規追加ではなく、既存項目の文言修正として扱う。

### 5. 重複を確認する

`team.md`と`common.md`を読み、類似のチェックがすでに存在しないか確認する。既存強化に分類したものは、ここで該当箇所を特定する。各新規項目について、追加先のセクション(既存の`##`見出し)を決める。合うセクションがなければ新しいセクションを提案する。

### 6. 承認を得てから更新する

提案するチェック項目を分類ごとに一覧表示し、`team.md`・`common.md`への実際の追記案(diffの形)をユーザーに提示する。**ユーザーが承認するまでファイルを書き換えない。** 承認後に追記し、変更点のサマリーを表示する。

## 書式

追加する項目は、既存項目と同じチェックリスト形式で、該当セクションの末尾に置く:

```markdown
- [ ] <何を見るか>(#<修正PR番号>より)
```

各項目には、それを生んだ修正PR番号を出典として残す。後で「なぜこのチェックがあるのか」を追跡できるようにするためだ。
