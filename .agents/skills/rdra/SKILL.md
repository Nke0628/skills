# RDRA

RDRA 3.0に基づく要求分析を支援するスキル。
RDRAの3フェーズで新規システムの要件定義を進める。
議事録・資料を `docs/rdra/inputs/` に置いて始め、次の往復をフェーズ1→2→3と繰り返して精度を上げる。

```
AIが叩き台を生成 → 不明点を質問 → 人が回答 → AIが反映する
```

## フェーズ

| フェーズ | やること                                                                | 次へ進む条件(`rdra.py gate`)                                                                                                 |
| -------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 1        | なぜ作るのか(ゴール・要求)と、業務の流れ(BUC・アクティビティ)を押さえる | 優先度・高の未解決0件。ゴールがあり、全ゴールに要求がつながっている。全BUCにアクティビティ、全アクティビティにアクターがある |
| 2        | システムで何をするか(UC・画面・イベント・情報・状態)を決める            | 優先度・高の未解決0件。致命的な構造の問題がない(どのUCにもつながらない情報など)                                              |
| 3        | 条件・バリエーションを詰め、整合性を確かめて完成させる                  | **完成:** 優先度・高・中の未解決0件。`仮説` の行がない。整合性チェックを満たすか「許容」と明記                               |

各フェーズで作るものは「phase1 / phase2 / phase3」を参照。

00_ゴール の計画の表(スコープ・完了の定義・マイルストーン・リスク)と `[計画]` の質問は、prd.html・diagrams.md に出し `rdra.py check` も指摘するが、上の判定には使わない。

完成すると git タグ `rdra-完成` が付く。完成の後に表・質問を変えると完成の記録は外れ、もう一度承認を経て `rdra-完成-2` が付く。

## モード

引数があればそのモード。なければユーザーの意図から選ぶ。意図がはっきりしなければ「状態の報告」をして次の操作を提案する。

| モード                         | 説明                                                               | 手順書                                             |
| ------------------------------ | ------------------------------------------------------------------ | -------------------------------------------------- |
| なし(状態の報告)               | 今どこにいて、次に何をすればいいかを伝える                         | `references/status.md`                             |
| `phase1` / `phase2` / `phase3` | 叩き台を作る・次のフェーズに進む                                   | `references/phase1.md` / `phase2.md` / `phase3.md` |
| `apply`                        | 質問への回答、表の直接編集、追加資料を反映する                     | `references/apply.md`                              |
| `prd`                          | 関係者とのMTG資料を作る                                            | `references/prd.md`                                |

各モードは、手順書を読んでから作業する。

## 成果物

```
docs/rdra/
├── inputs/              　　　　# 議事録・参考資料・要望のメモ(人が置く)
├── checklist-local.md   　　　　# このプロジェクト固有の質問観点
│
├── 00_ゴール.md               　# 背景・ゴールと計画(スコープ・完了の定義・マイルストーン・リスク)
├── 01_要求.md               　　# 要求
├── 02_アクター.md               # アクター・外部システム
├── 03_BUC.md            　　　　# BUC・アクティビティ・UC・画面・イベント
├── 04_情報.md               　　# 情報・情報の関連
├── 05_状態.md               　　# 状態モデル・状態遷移
├── 06_条件.md               　　# 条件・バリエーション
│
├── questions.md         　　　　# 質問と回答(AIが出し、人が回答する)
├── answers.json         　　　　# questions.html で入力した回答(apply で取り込む)
│
├── questions.html       　　　　# 質問の回答画面
├── prd.html             　　　　# 関係者MTG用の資料
├── diagrams.md          　　　　# Mermaid図
├── analysis.md          　　　　# 規模・整合性チェック・重要UC
├── status.md            　　　　# 現在のフェーズと次の判定
└── .state.json          　　　　# システム名・フェーズ・--force・許容・完成の記録
```

- 表(00〜06)は AIと人が書く。形式は `references/table-format.md`
- questions.html 以下はスクリプトの生成物。手で編集しない

## トレーサビリティ

表の参照列で次のように要素をつなぎ、どの要素も「なぜ必要か」を根(ゴール、またはゴールを持たないポリシー)までたどれるようにする。

```
ゴール
└── 要求
    └── BUC
        └── アクティビティ
            └── UC
                ├── 画面 / イベント
                ├── 情報 ── 状態
                └── 条件 ── バリエーション
```

用語と関係の詳細は `references/model.md`。

## 人がやること

ユーザーに次の操作を案内するときはこのとおりに伝える。どちらも最後に `/rdra apply` で反映される。

- **質問に答える:** `docs/rdra/questions.html` をブラウザで開き、優先度・高から回答して「回答を保存」で `answers.json` に書き出す(Chrome は直接保存。それ以外はダウンロードされるので `docs/rdra/` に置く)。MTG中のメモはメモ欄へ書き、「議事メモをコピー」して `inputs/議事録_日付.md` に保存すれば次の apply で取り込まれる。
- **表を直接直す:** `00_ゴール.md` 〜 `06_条件.md` は直接編集してよい。apply 時に git の差分から検出し、編集された行は `回答` になる。
- 人が確認すべきなのは出典が `仮説` の行だけ。

## 原則

1. **推測で確定させない。** 書く行には必ず出典を付ける。

   | 出典                | 意味                                                                  |
   | ------------------- | --------------------------------------------------------------------- |
   | `資料:<ファイル名>` | `docs/rdra/inputs/` の資料に記載がある                                |
   | `回答`              | 人の回答、または人の直接編集で確定した                                |
   | `仮説`              | AIの提案。**質問列に質問IDが必須。** 質問のない仮説を書いてはいけない |

2. **AIは勝手に削除しない。** 削除したいときは質問を出す。追加は `仮説 + 質問` で行ってよい。
3. **一つずつ完成させない。** まず全体を粗く埋め、つながりから精度を上げる。迷ったものは消さずに仮説として残し、質問する。
4. **人の書いたものをAIの判断で書き換えない。** `回答` の行も、inputs/ の資料も。矛盾を見つけたら質問を出す。
5. **用語と形式は決まりに従う。** 用語は `references/model.md`、表の形式は `references/table-format.md`。

質問を作るときは必ず次を読む: `references/questions.md`、該当フェーズの `references/checklist-phaseN.md`、`docs/rdra/checklist-local.md`。

## 共通ルール

表・質問を書くモードは、次の流れの「作業」の部分だけが違う。各モードの手順書には作業の部分とコミットメッセージだけが書いてある。

```
書く前   : init → 人の未コミット編集をコミット →(完成済なら reopen)
作業     : 各モードの手順書に従う
書いた後 : check → 生成物の更新 → コミット → 報告
```

### 書く前

1. `rdra.py init` を実行する(足りないファイルを空で足すだけで、既存のファイルは変えない)。
2. `git status --porcelain docs/rdra` で人の未コミットの編集を確認する。あれば `git add docs/rdra && git commit -m "rdra: 人の編集を取り込み"` する(apply ではその差分を解釈する)。
3. **完成の後に表・質問を書くとき:** `.state.json` の `done` が true なら、`rdra.py reopen "<操作と理由>"` を実行し、完成を外したことを報告する。完成に戻すのは `apply.md`「完成処理」の手順(人の承認)だけ。既存のタグ `rdra-完成` は消さない。

### 書いた後

1. `rdra.py check` — 致命の指摘が自分の書いた行にあれば直す
2. `rdra.py diagrams` / `rdra.py html` / `rdra.py prd` / `rdra.py status`
3. `git add docs/rdra && git commit -m "rdra: <操作> (<概要>)"`
   - コミットの対象は `docs/rdra/` だけ
   - 例: `rdra: phase1 生成`、`rdra: apply (Q-001〜Q-008 反映)`
4. 下の「報告」に従って報告する


### 判定と --force

- `phase2` / `phase3` の最初に `rdra.py gate 1` / `rdra.py gate 2` を実行する。満たしていなければ理由を示して止まる。満たしていれば `rdra.py set-phase 2` / `3` を実行する。
- ユーザーが `--force <理由>` を付けたときだけ、`rdra.py set-phase N --force "<理由>"` で進める。理由がなければ尋ねる。
- `set-phase` は今より小さい番号を渡しても何もしない(フェーズ番号は戻さない)。2回目の phase1・phase2 でもそのまま実行してよい。

### 報告

チャットでの報告は短くする。

- 書いた行数、仮説の行数
- 出した質問の数(優先度・高は件名も)
- 次にやること

成果物の中身はチャットに貼らない。最後に `docs/rdra/questions.html` を開くよう案内する。
