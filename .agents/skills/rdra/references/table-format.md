# 表の形式

`rdra.py` が読むため、見出し名・列名・列順を**厳密に**守る。表は `## <表名>` 見出しの直後に置く。全ての表の末尾2列は `出典 | 質問`。

## ファイルと列

### 00_ゴール.md

`## ゴール`
| ID | ゴール | 達成の判断基準 | 説明 | 出典 | 質問 |
|---|---|---|---|---|---|
| G-01 | 会員が電話をかけずに予約できる | Web予約の割合が全予約の6割以上 | 電話受付の負担を減らす | 要望 | |

- ID は `G-01` 形式。ゴールはシステムで達成したいこと、達成の判断基準はそれが達成できたと判断する基準(完成の定義)。要件定義の完成(`rdra.py gate done`)とは別。
- 1〜3件。最重要要求から作る。初期要望の原文とその後の決定が食い違うときは、決定に合わせる(初期要望.txt は直さない)。
- 判断基準はできるだけ数値・観測できる状態で書く。成功の指標(KPI)は要求ではなくここに書く。

### 01_要求.md

`## 要求`
| ID | 種別 | 要求 | 説明 | ゴールID | 出典 | 質問 |
|---|---|---|---|---|---|---|
| R-01 | 機能 | 会員がWebから予約できる | 電話予約の負担を減らす | G-01 | 要望 | |

- ID は `R-01` 形式。種別は `機能` / `非機能` / `ポリシー`。
  - 機能: システムでできること(入力する、計算する、表示するなど)。
  - 非機能: 機能をどれだけ快適・安全に使えるか(速さ、使える端末、個人情報の守り方など)。
  - ポリシー: システムの作り方ではなく、事業・運営として決めること(料金、だれ向けのサービスか、データをいつ消すか、制度改正への追従など)。PRDでは「方針」と表示する。
  - 両方にまたがるものは分ける。例: 「制度改正に追従する」はポリシー、「制度を計算に反映する」は機能。
- ゴールID は、その要求が支えるゴール(複数は `、` 区切り)。機能・非機能は必ずつなぐ。ポリシーは制約(料金、問い合わせ窓口など)が多いので、つながるものだけでよい。

`## アクター`

|---|---|---|---|

`## 外部システム`
| 外部システム | 説明 | 出典 | 質問 |
|---|---|---|---|

### 03_BUC.md

`## BUC`
| 業務 | BUC | 要求ID | 先 | アクティビティ | 次 | アクター | UC | 画面 | イベント | 外部システム | 情報 | 条件 | 出典 | 質問 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 予約業務 | Webで予約を受け付ける | R-01 | | 空き枠を探す | ↓ | 会員 | 空き枠を照会する | 空き枠検索画面 | | | 予約枠 | | 仮説 | Q-004 |
| 予約業務 | Webで予約を受け付ける | R-01 | | 予約を申し込む | ↓、満席 | 会員 | 予約を登録する | 予約入力画面 | | | 予約、会員 | | 要望 | |
| 予約業務 | Webで予約を受け付ける | R-01 | | 予約を確定する | | 店舗スタッフ | | | | | 予約 | | 要望 | |
| 予約業務 | キャンセル待ちを受け付ける | R-06 | 満席 | キャンセル待ちに登録する | | 会員 | | | | | 予約 | | 要望 | |

- 1行 = 1アクティビティ(1つのアクティビティに複数のUCがあれば、同じアクティビティ名で複数行)。
- **業務・BUCは同じ値が続いても毎行書く。**
- アクティビティのつながり(業務フロー)は 先・次 の列で書く。RDRA公式の表形式(RDRA定義シートの C列・E列)と同じ決まり。
  - 次 に `↓`: 同じ業務の、すぐ下の行のアクティビティへ進む(下の行が別のBUCでもよい)。
  - 次 にラベル: 同じ業務で、先 に同じラベルを書いたアクティビティへ進む。ラベルは短い名詞(`受理`、`入金差異` など)。
  - 次 に複数(`↓、入金差異` など `、` 区切り): 流れが分かれる。並行か条件による分岐かは表では区別しない。分岐の条件はフェーズ3で条件として表す。
  - 次 が空: そこで流れが終わる(つながらない)。
  - 先 は、ほかの行から飛んでくるアクティビティにだけ書く。同じ業務の中でラベルを重ねない。業務をまたいではつながない。
- 同じアクティビティが複数行(UCが複数)のときは、先・次を最初の行に書く。
- 行は流れの順(`↓` でつながる順)に並べる。BUCどうしも、利用者が経験する順(始める → 使う → やめる)に並べる。
- BUCの途中のアクティビティ(BUCの最後以外)には次を書く。BUCは待ちが入らずに一区切りまで進む流れなので、途中で切れない。
- フェーズ1では UC・画面・イベント・条件の列は空でよい。先・次はフェーズ1で書く。情報の列には、そのアクティビティで扱う情報を書いてよい。
- アクティビティにはアクターか外部システムのどちらかが必須。
- システムを使わない人の作業のアクティビティは、UCを空にする。

### 04_情報.md

`## 情報`
| コンテキスト | 情報 | 説明 | 属性 | 状態モデル | バリエーション | 出典 | 質問 |
|---|---|---|---|---|---|---|---|

`## 情報関連`
| 情報 | 関連先 | 多重度 | 出典 | 質問 |
|---|---|---|---|---|

- 多重度は `1対1` / `1対多` / `多対1` / `多対多`。
- 属性は主要な項目だけを `、` 区切りで書く(キーになるIDを先頭に)。
- 状態モデルは、その情報が持つ状態モデルを 05_状態 の名前と完全に一致させて書く。持たなければ空。1つの状態モデルは1つの情報に持たせる。
- バリエーションは、その情報が値として持つバリエーションを 06_条件 の名前と完全に一致させて書く(複数は `、` 区切り)。対応する項目を属性にも書く。フェーズ2では空でよく、フェーズ3で埋める。どの情報も持たないバリエーション(ルールの区分など)もある。

### 05_状態.md

`## 状態`
| コンテキスト | 状態モデル | 状態 | 遷移先 | 遷移UC | 出典 | 質問 |
|---|---|---|---|---|---|---|

- 1行 = 1つの状態からの遷移。同じ状態から複数の遷移先がある場合は行を分ける。
- 遷移先のない状態(終端、またはフェーズ1で名前だけ)は遷移先・遷移UCを空にする。
- 遷移UC は 03_BUC の UC 列にある名前と完全に一致させる。

### 06_条件.md

`## 条件`
| コンテキスト | 条件 | 説明 | バリエーション | 状態モデル | 出典 | 質問 |
|---|---|---|---|---|---|---|

`## バリエーション`
| コンテキスト | バリエーション | 値 | 出典 | 質問 |
|---|---|---|---|---|

`## 条件の表`
| 条件 | 値 | 結果 | 出典 | 質問 |
|---|---|---|---|---|

- 条件の表は、条件の結果を軸(バリエーション・状態)の値の組合せごとに書く。1行が1つの組合せ。
- 値は、条件のバリエーション列の順、続けて状態モデル列の順に、軸ごとに1つずつ `、` 区切りで書く。値は 06_条件 のバリエーションの値、または 05_状態 の状態と完全に一致させる。
- 軸の値を問わないときは `すべて`、同じ結果になる値をまとめるときは `/` で区切る(例: `住宅ローン(フラット35)/住宅ローン(その他)、すべて`)。
- 結果は、その組合せで何が起きるかを短く書く。計算式は書かない。
- 組合せで結果が分かれず、説明の文章で足りる条件には行を書かない。
- PRD では、軸が1つなら値と結果の表、2つなら縦横の表、3つ以上なら組合せの一覧として出す。

## 共通の規則

- 1つのセルに複数の値を入れるときは `、` で区切る。
- 他の表の要素を参照するときは、定義された名前と**完全に一致**させる(表記揺れは参照切れになる)。
- セル内で `|` を使うときは `\|` と書く。
- 行の出典が `仮説` のとき、質問列に `Q-012` のように質問IDを書く(複数は `、` 区切り)。
- 出典は行単位。1つの行の一部だけが仮説なら、行を `仮説` にして、質問で仮説の部分を明示する。
- 表の外(見出しの下の説明文など)は自由に書いてよいが、`## <表名>` 見出しの直後に別の表を置かない。
