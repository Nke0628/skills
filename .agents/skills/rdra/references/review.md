# review: レビューエージェントで成果物を見直す

`rdra.py check` は1段のつながり、`rdra.py trace` は根(ゴール・ポリシー)までの到達を機械的に見る。review は、別の文脈のサブエージェントに、つながりが**意味をなしているか**(なぜ・どう実現するかが本当に説明できるか)を中心に、出典・曖昧さ・矛盾を見させる。指摘は質問にして人に判断してもらう。

## いつ使うか

- `/rdra review [all|trace|source|ambiguity|consistency]` で呼ばれたとき
- 完成の承認を求める前(`apply.md`「完成処理」)
- フェーズの叩き台を作った直後など、まとめて見直したいときに、次の操作として提案してよい(自動では起動しない)

## 手順

### 1. レビューエージェントを起動する

Agent tool で起動する。

- `subagent_type`: `general-purpose`
- `run_in_background`: `false`(次の手順で結果を読むので、終わるまで待つ)
- `prompt`: 次の内容を渡す。自分の作業の経緯や意図は渡さない(先入観なしに読ませるため)

```
.agents/skills/rdra/agents/reviewer.md を読み、その手順に従ってレビューしてください。
リポジトリのルート: <絶対パス>
レビュー対象: <all など>
```

### 2. 指摘を確かめる

`docs/rdra/review.md` を読み、指摘ごとに対象の行と根拠を自分でも確かめる。

- 誤った指摘(根拠の引用が実際と違う、フェーズで書かない列を指摘している等)は採らない。review.md の該当の指摘の末尾に `- **判断**: 不採用(理由)` と書き足す。
- それ以外は採る。

### 3. 質問にする

採った指摘は、`references/questions.md` の書式で質問にする。

- 優先度は `references/questions.md`「優先度の基準」で付け直す。指摘の重要度は参考にとどめる(重要度・高でも、次のフェーズに進めなくなるほどでも手戻りが大きいわけでもなければ中にする)。優先度・高の最大10問の上限も守る。超えた分は質問にせず、review.md の指摘の末尾に `- **判断**: 次回` と書き足す(次のレビューで引き継がれる)。
- `根拠:` には、指摘の問題を業務の言葉で書き直す。指摘のIDや行番号は書かない(`references/questions.md`「良い質問」)。行番号は、アクティビティ・操作・ルールの名前に置き換える。
- 対象が `仮説` の行なら、行の質問列に新しい質問IDを足す。`要望` / `資料` / `回答` の行は書き換えず、質問だけを出す(原則4)。出典の偽りが疑われる行も、勝手に `仮説` に戻さず質問で確かめる。
- 自分が書いた `仮説` の行の表記揺れ・命名規則の逸脱(重要度・低)は、質問を出さずに直してよい。名前を直したら、`apply.md`「波及先を確認する」の名前の変更と同じく、参照している行の名前も揃える。直したことを review.md の指摘の末尾に `- **判断**: 修正済` と書き足す。
- review.md の採った指摘の末尾に `- **判断**: Q-NNN` と書き足す。

### 4. 仕上げ

コミットする(メッセージ `rdra: review (指摘 N件、質問 M件)`)。

## 報告

観点ごとの指摘の件数、採らなかった件数、出した質問の数(優先度・高は件名)、次にやること。指摘の詳細はチャットに貼らず、`docs/rdra/review.md` を案内する。
