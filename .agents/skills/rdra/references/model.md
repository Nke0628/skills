# RDRAモデル

出典: https://www.rdra.jp/ (どんな手法? / 表形式のRDRA定義 / RDRAビジュアル分析)

## 4つのレイヤー

要件定義は4つの視点でできている。内側から外側へ依存し、レイヤー間のつながりが「Why」を表す。

| レイヤー | 視点 | このスキルでの要素 |
|---|---|---|
| システム価値 | システムが価値をもたらす | ゴール、要求(機能要求・非機能要求・ビジネスポリシー)、アクター、外部システム |
| システム外部環境 | システムが使われる環境 | 業務、BUC、アクティビティ、条件、バリエーション |
| システム境界 | システムとの境界 | UC、画面、イベント |
| システム | システムそのもの | 情報、状態、コンテキスト |

## 要素

| 要素 | 意味 | 命名・粒度 |
|---|---|---|
| ゴール | システムで達成したいことと、その達成の判断基準。要求の「なぜ」 | 1〜3件。判断基準はできるだけ数値で |
| 要求 | システムに求められること。BUCの「なぜ」 | 機能要求 / 非機能要求 / ビジネスポリシー(業務上の決まり事)に分類 |
| アクター | システムに関わる人の**役割** | 個人名・部署名ではなく役割名(「店舗スタッフ」) |
| 外部システム | 連携する他システム。価値につながるもの(顧客のシステム等)を含む | システム名 |
| 業務 | 1つの目的のために、同じ「主役」(中心になる情報・モノ)を追いかけて回る仕事のまとまり。分け方は下の「業務・BUC・アクティビティの粒度」 | 名詞句(「オーダー業務」「出荷業務」「商品企画業務」) |
| BUC | 業務の中で、1つのきっかけから始まり、待ちが入らずに一区切りまで進む流れ。終わると主役の状態が進む。状態を進めないもの(入力だけ、ログイン、閲覧だけなど)はBUCにせず、別のBUCのアクティビティかUCにする | 「〜する」(「注文を受け付ける」「入金を確認して出荷を指示する」) |
| アクティビティ | BUCの中で、誰か(1つの役割、または外部システム)が行う1つの作業。人の作業もシステム利用も含む | 「〜を〜する」(「オーダーを確認する」) |
| UC | アクティビティの中でシステムを使う部分 | **「XXXをYYYする」**(「予約を登録する」) |
| 画面 | UCとアクターの入出力 | 「〜画面」 |
| イベント | UCと外部システムの入出力 | 「〜通知」「〜連携」。時刻起動は「タイマー:〜」 |
| 情報 | システムが保持するもの | **ID単位**(請求書番号・受注番号など業務で管理するキー)で洗い出す |
| 状態 | 情報の変化。状態モデル(情報ごと)の中の状態 | 状態モデル名は「〜状態」、状態は「予約済」「キャンセル済」 |
| 条件 | ビジネスルール | 「〜判定」「〜の可否」など |
| バリエーション | 条件の軸になる種類・区分。値を列挙する | 「会員種別: 一般、プレミアム」 |
| コンテキスト | 役割の同じ情報のまとまり。状態モデル・条件・バリエーションは関係の深い情報のコンテキストに入れる | 名詞(「予約」「会員」) |

## 業務・BUC・アクティビティの粒度

### 判断の問い

| 要素 | 判断の問い | 境界のサイン |
|---|---|---|
| 業務 | 主役(中心になる情報・モノ)は同じか / 目的・成果は同じか / 回るサイクル(1件ごと・定期的にまとめて)は同じか | 主役が変わる、件数の対応が 1:1 から N:1 に変わる(複数のオーダーを締めでまとめて出荷する等)、目的が変わる |
| BUC | きっかけ(イベント)は1つか / 途中で「待ち」が入らずに進むか / 終わったとき主役の状態が変わっているか | 待ちが発生する、きっかけが変わる(店頭の受付とWebの受付など)、例外ルートとして独立して扱いたい |
| アクティビティ | 1人(1つの役割)が行う作業か / 「〜を〜する」と1文で言えるか / システムを使うなら1つのUCに対応しそうか | 担当(役割)が変わる、作業の対象が変わる |

例: 業務「オーダー業務」のBUC「注文を受け付ける」「入金を確認して出荷を指示する」「入金差異を解消する」。BUC「入金を確認して出荷を指示する」のアクティビティ「入金を確認する」「出荷を指示する」。

### 迷ったときの順番

1. 主役は何か → 主役が変われば別の業務
2. その主役の状態はどう変わるか → 状態の変化1つ(または数個)ごとにBUC。状態は 05_状態 と突き合わせる
3. 状態を進めるために誰が何をするか → 担当と作業ごとにアクティビティ

### 粒度のずれの症状

| 症状 | 原因 |
|---|---|
| BUCで主役の状態が変わらない | アクティビティを切り出しすぎ。どこかのBUCのアクティビティかUCにまとめる |
| 1つのBUCで状態がいくつも飛ぶ | 待ちを見落としていて粗すぎ。待ち・きっかけで分ける |
| 業務の流れに N:1 の集約が入る | 別の業務が混ざっている。集約の先を別の業務にする |

## 関係

```
ゴール
└── 要求
    └── BUC ── 業務
        └── アクティビティ ── アクター / 外部システム
            └── UC
                ├── 画面 ── アクター
                ├── イベント ── 外部システム
                ├── 情報 ── 状態(UCが状態を遷移させる)
                └── 条件 ── バリエーション / 状態
```

- UC同士は直接関わらず、情報を介して整合する。
- 条件はバリエーションの組合せ、またはバリエーションと状態の組合せで表す。組合せごとの結果は、06_条件 の条件の表に書く。
- バリエーションは情報の項目として関わる(04_情報 のバリエーション列で示す)。ビジネスの変化はバリエーションの値の追加・変更として現れることが多い。

## 重要UC

- 複数のコンテキストにまたがるUC
- 複数の状態モデルを変えるUC

開発の優先順位づけに使う(`rdra.py analysis` が抽出する)。
