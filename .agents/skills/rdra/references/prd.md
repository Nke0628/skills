# prd: 関係者MTG用のPRDを作る

目的: 非エンジニアを含む関係者と、今の要件定義の内容を読み合わせて議論する。MTGで出た意見は議事録として `inputs/` に戻し、apply で反映する。

## 手順

1. `rdra.py prd` を実行し、`docs/rdra/prd.html` を作る。中身は表と questions.md から機械的に作られる。**AIがPRDに文章を書き足したり、手で直したりしない。** 表現を変えたいときは表を直してから作り直す。
2. 作ったPRDを読み、MTGの前に気づいたことを報告する(PRDには書かない)。
   - 優先度・高の未解決の質問。MTGで決めるべき論点として挙げる。
3. コミットする(メッセージ `rdra: prd 生成`)。

## PRDの構成

| 節 | 中身 | 元 |
|---|---|---|
| 背景 | 背景の一覧 | 00_ゴール |
| 目的 | ゴールの表(ID・ゴール・達成の判断基準・説明) | 00_ゴール |
| スコープ | スコープの表(ID・区分・内容・理由)。システムが扱う範囲の線引き | 00_ゴール |
| 完了の定義 / マイルストーン / リスク | それぞれ表で出す。目的からリスクまでは、空なら「まだ決まっていない」 | 00_ゴール |
| システムコンテキスト | システムを中心にアクター・外部システムをつないだ図と、それぞれの説明 | 02_アクター |
| 要求 | 要求を「機能 / 非機能 / 方針(種別ポリシー) / 対象外」に分け、見出しの下にそれぞれ何を入れるかを1行で示す。対象外はやらない理由(説明)を添える | 01_要求 |
| 業務フロー | 先頭に、見出し「ビジネスコンテキスト」で、業務と関わるアクター・外部システムを線でつないだ図(BUCは描かない)(向きなし。仮説の行でしか関わらない線は点線。業務が1つなら出さない)。続けて業務ごとに、見出し「ビジネスユースケース」でその業務の枠の中にBUCを置き、BUCごとに関わるアクター・外部システムを線でつないだ図、見出し「業務フロー」で業務の全アクティビティをアクターのレーンに置いて先・次のとおりに矢印でつないだ業務フロー図を出し、その下にBUCごとに(見出しは「BUC - <BUC名>」)、そのBUCのアクティビティだけの図(ほかのBUCとのつながりは「BUC「X」へ/から」で示す。5つ以上は縦並び)。アクター・外部システムはUC複合図と同じ形・色で描く。アクティビティごとの詳細はたたんで表示し、UCがあればUC複合図(ロバストネス図にならい、画面・イベントを「バウンダリ」、UCを「コントローラ」、情報・状態モデルを「エンティティ」の枠に置き、アクター・外部システム・条件は枠の外に置く。画面・イベント・情報・条件・状態とのつながり。状態モデルはUCではなく持ち主の情報につなぎ、その線にこのUCで起きる遷移を書く。持ち主の情報をUCが扱っていなければ状態モデルは描かない。要素ごとに種類を書き、色で分ける。情報・条件・状態モデルは押すと中身を小窓に出す。情報の小窓には説明・コンテキスト・主な項目と、状態モデルの状態・バリエーションの値を出し、つながる情報や扱うUCは出さない。条件の小窓にも使うUCは出さない)で示す | 03_BUC |
| 情報 | 情報の関連を左から右にたどる図(矢印に多重度)と、コンテキストごとの表(主な項目、状態・バリエーションとその値、使うアクティビティ) | 04_情報 |
| 状態遷移 / 条件 | 状態モデルごとの状態遷移図(遷移が書かれていれば、05_状態 の最初の行の状態に開始の印、入ってくるが出ていかない状態に終了の印を付ける。遷移UCが4つ以上なら「〜など N件」と縮める)、条件・バリエーション(あるときだけ)。条件の表がある条件は、説明の下に表を出す(軸が1つなら値と結果、2つなら縦横の表、3つ以上なら組合せの一覧。書かれていない組合せは「未定」) | 05_状態、06_条件 |
| これまでに決まったこと | 反映済の質問と回答 | questions.md |
| 議論したいこと | 未解決の質問(提案・理由・選択肢)と仮説の行 | questions.md、全表 |
| 議事メモ | 各項目のメモ欄をまとめてコピーする | — |

diagrams.md も、背景からリスクまでを同じ章立てで冒頭に出す(仮説の行は「(仮説)」を付ける)。要求の章は、要求の表(ID・種別・要求・説明・ゴールID)を種別の順(機能・非機能・ポリシー・対象外)に並べて出す。情報(コンテキストごとの表と情報のつながり)、状態遷移(移り変わりの表)、条件(条件ごとの説明と条件の表、バリエーション)も PRD と同じ中身を表で出す。これまでに決まったこと・議論したいことは questions.md と重なるので出さない。図は diagrams.md と同じ Mermaid で描き、prd.html は cdnjs の Mermaid で表示する(オフラインでは図の元の記述が文字で出る)。たたんだ欄の中の図は、開いたときに描く。図の先頭で配置(`layout: dagre`)を固定し、Mermaid のバージョンが違う表示環境(Markdown のプレビューなど)でも同じ形にする。

見出しにかっこ書きの言い換えを付けない。読み手に不要な生成元の説明(「docs/rdra の表から生成」、資料のファイル名など)は書かない。

見出しと本文は、RDRAの用語を言い換えずに使う(スコープ、完了の定義、システムコンテキスト、アクター、外部システム、要求、ビジネスコンテキスト、BUC、アクティビティ、UC、情報、コンテキスト、状態遷移、条件、バリエーション)。用語の意味は「この資料の読み方」の欄で説明する。出典のラベル(資料・決定など)、本文の質問番号「(Q-001)」、フェーズ名、要求ごとの「実現するBUC」は出さない。AIの仮説は図の点線と「議論したいこと」で示す。

## MTGのあと

人が「議事メモをコピー」でまとめたものを `docs/rdra/inputs/議事録_YYYYMMDD.md` に保存し、`/rdra apply` で追加資料として反映する。

## 報告

prd.html のパス、未解決の質問の数(優先度・高は件名)、MTG前に気づいた食い違い、MTG後の流れ(議事メモ → inputs → `/rdra apply`)を短く伝える。
