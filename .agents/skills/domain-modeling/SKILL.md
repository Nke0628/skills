# Domain Modeling

設計を進めながら、プロジェクトのドメインモデルを能動的に構築し、研ぎ澄ます。これは*能動的な*規律だ。用語に異議を唱え、エッジケースのシナリオを考案し、それが結晶化した瞬間に用語集と決定を書き留める。(単に語彙のために`CONTEXT.md`を*読む*だけなら、これはこのスキルではない。それはどのスキルでもできる1行の習慣にすぎない。このスキルは、モデルを単に消費するのではなく、変更しているときのためのものだ。)

## ファイル構成

ほとんどのリポジトリには単一のコンテキストしかない:

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

ルートに`CONTEXT-MAP.md`が存在すれば、そのリポジトリは複数のコンテキストを持つ。マップは、それぞれがどこにあるかを示す:

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← システム全体の決定
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← コンテキスト固有の決定
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

ファイルは遅延生成する: 書くべきことがあるときだけ作る。`CONTEXT.md`が存在しなければ、最初の用語が確定した時点で作成する。`docs/adr/`が存在しなければ、最初のADRが必要になった時点で作成する。

## セッション中に

### 用語集と照らして異議を唱える

ユーザーが`CONTEXT.md`にある既存の言葉と矛盾する用語を使ったら、その場ですぐに指摘する。「あなたの用語集では『cancellation』はXと定義されているが、あなたが言っているのはYのようだ。どちらか?」

### 曖昧な言葉を研ぎ澄ます

ユーザーが曖昧な用語や多義的な用語を使ったら、正確な正典の用語を提案する。「『account』と言っているが、CustomerのことかUserのことか? それらは別物だ。」

### 具体的なシナリオで議論する

ドメインの関係が議論されているときは、具体的なシナリオでそれを検証する。エッジケースを探るシナリオを考案し、ユーザーに概念間の境界を正確にするよう求める。

### コードと照らし合わせる

ユーザーが何かの動作について述べたら、コードがそれと一致しているか確認する。矛盾が見つかったら明るみに出す。「あなたのコードはOrder全体をキャンセルしているが、たった今、部分的なキャンセルも可能だと言った。どちらが正しいのか?」

### CONTEXT.mdをその場で更新する

用語が確定したら、その場で`CONTEXT.md`を更新する。まとめて後回しにせず、発生した瞬間に捉える。[CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)にある形式を使う。

`CONTEXT.md`は実装の詳細を一切含んではならない。`CONTEXT.md`を仕様書、スクラッチパッド、実装決定の保管庫として扱わない。それは用語集であり、それ以外の何物でもない。

### ADRは控えめに提案する

以下の3つすべてが真であるときに限り、ADRの作成を提案する:

1. **後戻りしにくい**: 後で考えを変えるコストが無視できない
2. **文脈がないと意外に映る**: 未来の読み手が「なぜこんなやり方をしたのか?」と疑問に思うだろう
3. **本物のトレードオフの結果である**: 本当の代替案があり、特定の理由でその一つを選んだ

3つのうちどれか1つでも欠けていれば、ADRは見送る。[ADR-FORMAT.md](./ADR-FORMAT.md)にある形式を使う。
