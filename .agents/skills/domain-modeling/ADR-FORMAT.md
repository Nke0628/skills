# ADR フォーマット

ADRは`docs/adr/`に置き、連番を使う: `0001-slug.md`、`0002-slug.md`など。

`docs/adr/`ディレクトリは遅延生成する: 最初のADRが必要になった時点でのみ作る。

## テンプレート

```md
# {決定の短いタイトル}

{1〜3文: 文脈は何か、何を決めたか、そしてなぜか。}
```

これだけでよい。ADRは1段落でも構わない。価値があるのは、決定が*なされたこと*とその*理由*を記録することであり、セクションを埋めることではない。

## 任意のセクション

これらは本当に価値を加える場合にのみ含める。ほとんどのADRには不要だ。

- **Status**のフロントマター(`proposed | accepted | deprecated | superseded by ADR-NNNN`): 決定が後で見直される場合に有用
- **Considered Options(検討した選択肢)**: 却下した代替案が記憶に値する場合のみ
- **Consequences(結果)**: 非自明な下流への影響を指摘する必要がある場合のみ

## 番号付け

`docs/adr/`をスキャンして既存の最大番号を見つけ、1を足す。

## いつADRを提案すべきか

以下の3つすべてが真でなければならない:

1. **後戻りしにくい**: 後で考えを変えるコストが無視できない
2. **文脈がないと意外に映る**: 未来の読み手がコードを見て「一体なぜこんなやり方をしたのか?」と疑問に思うだろう
3. **本物のトレードオフの結果である**: 本当の代替案があり、特定の理由でその一つを選んだ

決定が簡単に覆せるなら見送る。どうせ覆すことになるからだ。意外でないなら、誰もその理由を疑問に思わない。本当の代替案がなかったなら、「当たり前のことをした」以上に記録すべきことは何もない。

### 該当するもの

- **アーキテクチャの形。** 「モノレポを使っている。」「書き込みモデルはイベントソーシングで、読み取りモデルはPostgresに投影されている。」
- **コンテキスト間の統合パターン。** 「OrderingとBillingは同期HTTPではなく、ドメインイベントを通じて通信する。」
- **ロックインを伴う技術選定。** データベース、メッセージバス、認証プロバイダ、デプロイ先。すべてのライブラリではなく、置き換えに四半期かかるようなものだけ。
- **境界とスコープの決定。** 「顧客データはCustomerコンテキストが所有し、他のコンテキストはIDでのみそれを参照する。」明示的な「やらないこと」は「やること」と同じくらい価値がある。
- **明白な道からの意図的な逸脱。** 「Xという理由でORMではなく手書きSQLを使っている。」まっとうな読み手が逆を想定してしまいそうなもの全般。これにより、次のエンジニアが意図的だったものを「修正」してしまうのを防ぐ。
- **コードに現れない制約。** 「コンプライアンス要件のためAWSは使えない。」「パートナーAPIの契約により、応答時間は200ms未満でなければならない。」
- **却下が非自明な場合の、却下した代替案。** GraphQLを検討し、微妙な理由でRESTを選んだのなら、それを記録する。さもないと、半年後に誰かがまたGraphQLを提案してくる。
