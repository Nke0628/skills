# ブラウザ記録のルール

フェーズ2は「仕様YAML(日本語の自然文)を実際のブラウザ操作で裏付ける」フェーズである。記録した内容がフェーズ3のコードにそのまま落ちるため、ここでの不正確さは全部下流に伝播する。

記録は**仕様YAMLとは別のファイル**に書く。仕様書に実装情報を混ぜないためである。仕様YAML1つにつき、対応する記録ファイルを1つ作る(例: `login.spec.yaml`の仕様に対して`login.recorded.yaml`)。

保存場所は仕様YAMLと同じディレクトリ(例: `e2e/specs/`)にする。仕様・記録・テストコードの3つを、対応関係が一目でわかる位置に揃えて管理する。

## 記録ファイルの構造

```yaml
spec: docs/specs/login.yaml
scenario: 正しい認証情報でログインできる
records:
  - step: ユーザーがログインページを開いている
    action: navigate
    target: /login
  - step: 正しいメールアドレスとパスワードを入力してログインボタンを押す
    action: fill
    target: '[data-testid="email-input"]'
    value: user@example.com
  - step: 正しいメールアドレスとパスワードを入力してログインボタンを押す
    action: click
    target: 'role=button[name="ログイン"]'
  - step: ダッシュボードに遷移する
    action: assert-url
    expected: /dashboard
```

- `step`: 仕様YAML側の文(`given`/`when`/`then`のいずれかの1文)をそのまま転記する。1文が複数の操作に分かれる場合は、同じ`step`の記録を複数並べる。
- `action`/`target`/`value`/`expected`: 実測した内容。推測や願望を書かない。

## 進め方

1. シナリオ単位で、前提から順にステップを実行する。前のステップが失敗した状態で次のステップを記録しない。
2. 各ステップの実行前に、対象要素が画面上に実在することを確認してからセレクタを確定する。存在しない要素へのセレクタを書かない。
3. 1ステップ実行するごとに、その場で記録ファイルに書く。まとめて後から埋めない(記憶で埋めると実測値からズレる)。

## セレクタの優先順位

1. `data-testid`(または同等のテスト専用属性)
2. アクセシビリティロール + ラベル/名前(`role=button[name="ログイン"]`など)
3. 可視テキスト
4. CSSセレクタ(構造依存で壊れやすいため最終手段)

以下は記録しない:

- インデックス依存のセレクタ(`nth-child(3)`など)。DOM順序の変更で壊れる。
- スタイル用クラス名(`.btn-primary`など)。見た目の変更で壊れる。

## アクション語彙

| action | 用途 |
| --- | --- |
| `navigate` | URL遷移 |
| `click` | クリック |
| `fill` | テキスト入力 |
| `select` | セレクトボックスの選択 |
| `check` / `uncheck` | チェックボックス操作 |
| `assert-visible` | 要素の可視性を確認 |
| `assert-text` | 要素のテキスト内容を確認 |
| `assert-url` | 現在のURLを確認 |
| `assert-attribute` | 要素の属性値(`target`/`rel`/`href`など)を確認 |

新しい語彙が必要になったら、この表に追記してから使う。場当たり的な独自語彙を増やさない。

## 仕様との食い違いを見つけたら

記録中に以下のいずれかに気づいたら、その場で止めてユーザーに報告する。フェーズ3に進んでから帳尻を合わせない。

- 仕様YAMLの文が指す要素が画面に存在しない
- 遷移先やメッセージが仕様書の記述と異なる
- シナリオの前提がUI操作だけでは再現できない(バックエンドの状態投入が必要など)
