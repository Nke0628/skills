# BDD仕様YAML フォーマット

フェーズ1で作る、**テスト仕様書として管理する**YAML。キーは英語、値(文章)はすべて日本語の自然文で書く。セレクタや操作名など実装を匂わせるものは一切含めない。実装情報(記録)はフェーズ2で別ファイルに分離する。

## 構造

```yaml
feature: ログイン
scenarios:
  - name: 正しい認証情報でログインできる
    given:
      - ユーザーがログインページを開いている
    when:
      - 正しいメールアドレスとパスワードを入力してログインボタンを押す
    then:
      - ダッシュボードに遷移する

  - name: 誤ったパスワードではログインできない
    given:
      - ユーザーがログインページを開いている
    when:
      - 正しいメールアドレスと誤ったパスワードを入力してログインボタンを押す
    then:
      - パスワードが正しくないというエラーメッセージが表示される
      - ログインページに留まる
```

## フィールド

- `feature`: シナリオ群のタイトル。仕様書の見出しかコード上の機能名。
- `scenarios[].name`: シナリオ名。仕様書があればその文言をそのまま使う。
- `given` / `when` / `then`: Given/When/Thenに対応する文の配列。「かつ」で続く文は同じ項目に配列の要素として追加する。

## ルール

- **キーは英語、値は日本語の自然文。** セレクタ、コード、`null`など、実装を匂わせるものは値に書かない。このYAMLだけを読めば、エンジニアでない人でも仕様がわかる状態を保つ。
- **1シナリオ1パスの正常系/異常系。** 複数の分岐を1シナリオに詰め込まない。仕様書の粒度をそのまま反映する。
- **このファイルが仕様の正本。** 実装(セレクタや画面構造)が変わっても、仕様そのものが変わらない限りこのファイルの文言は変えない。実装都合による変更はフェーズ2の記録ファイルだけに反映する。

## 実装情報の置き場所

セレクタ・操作・アサーションの実測値はこのファイルには書かない。フェーズ2で別ファイルとして記録する([RECORDING.md](RECORDING.md)参照)。仕様YAMLをドキュメントとして安定させ、実装の詳細は更新されやすい記録側に閉じ込めることで、仕様書としての可読性と寿命を保つ。

## 保存場所

このYAMLは**E2Eテストコードの近く**(例: `e2e/specs/`のように、既存のE2Eテストディレクトリと対になるサブディレクトリ)に置く。プロジェクトに既存のE2Eテストがあれば、その配置規則に合わせる。`.claude/skills/`配下などスキル自身のディレクトリには置かない — そこはスキルの定義であり、プロジェクトの仕様書の置き場所ではない。ファイル名はシナリオ対象の機能名に合わせる(例: `login.spec.yaml`)。
