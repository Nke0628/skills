# E2Eコード生成のルール

仕様YAML(前提/操作/確認の日本語文)と、フェーズ2の記録ファイル(`action`/`target`/`value`/`expected`が実測値で埋まっている)を突き合わせて、プロジェクトのE2Eフレームワークのコードに変換する。

## フレームワークの検出

1. `playwright.config.*`、`cypress.config.*`、`package.json`の`devDependencies`を確認する。
2. 複数存在する、またはどちらもない場合はユーザーに確認する。存在しないプロジェクトに新規導入する場合は、導入自体を提案してから進める(黙って依存を追加しない)。
3. 既存のE2Eテストが1つでもあれば、それを前例として構成・命名規則・ヘルパー関数を踏襲する。新しい規約を発明しない。

## 構成

- 1シナリオ = 1テスト(`test`/`it`)。1フィーチャー = 1ファイル、が既存の前例と衝突しない限りのデフォルト。
- BDDのGiven/When/Thenは、対応するフレームワークの機能(例: Playwrightの`test.step()`)かコメントとして残す。仕様YAMLの前提/操作/確認の文言をそのまま使い、コードだけを見ても元の仕様に戻れるようにする。

```ts
test("正しい認証情報でログインできる", async ({ page }) => {
  await test.step("Given: ユーザーがログインページを開いている", async () => {
    await page.goto("/login");
  });

  await test.step("When: 正しいメールアドレスとパスワードを入力してログインボタンを押す", async () => {
    await page.getByTestId("email-input").fill("user@example.com");
    await page.getByTestId("password-input").fill("correct-password");
    await page.getByRole("button", { name: "ログイン" }).click();
  });

  await test.step("Then: ダッシュボードに遷移する", async () => {
    await expect(page).toHaveURL("/dashboard");
  });
});
```

## ルール

- フェーズ2で記録した`target`をそのままセレクタに使う。コード生成時に「もっと綺麗そうな」セレクタへ書き換えない。動作確認済みの値を優先する。
- 待機は固定`sleep`ではなく、フレームワークの自動待機(要素の出現待ちなど)か、明示的な条件待ち(`waitForResponse`など)を使う。
- 認証やテストデータ準備など、複数シナリオで共通する前提は既存のヘルパー/フィクスチャを再利用する。無ければ、既存のテストが従う配置場所に合わせて新設する。
- 生成後はプロジェクトの型チェック/lintを実行し、フェーズ4に進む前に構文的な問題を潰す。

## レポート出力

E2Eフレームワークをプロジェクトに新規導入する場合、テストコードと合わせて以下も用意する。

- **失敗時に原因究明できる証跡**: スクリーンショット・動画・トレースを残すレポーター設定(Playwrightなら`use.screenshot`/`use.video`/`use.trace`と`html`レポーター)。
- **PRへの共有方法はプロジェクトに確認する。** インタラクティブなHTMLレポートはローカルサーバー(例: `playwright show-report`)でしか正しく閲覧できず、GitHubのPRにそのまま埋め込めない。代表的な選択肢は次の2つで、どちらを使うか・コミット対象にするかは既存の前例(過去のPRでの証跡の残し方など)を確認し、無ければユーザーに聞く。決め打ちしない。
  1. **ローカル限定・非コミット**: テスト実行後にレポート一式をzip化するnpmスクリプト(例: `test:e2e:report`)を用意し、そのzipをPRの説明欄・コメント欄にドラッグ&ドロップで添付する。生成物は`.gitignore`に追加し、コミット対象に含めない。
  2. **リポジトリにコミットしてPRの差分に含める**: `docs/<チケット名>/test/report/`のような、チケット/Issue単位のディレクトリに、PlaywrightのHTMLレポート一式(`index.html`と`data/`配下の画像・動画)をzip化せずフォルダごと配置してコミットする。チケット名はユーザーに確認する(Issue番号やブランチ名など、プロジェクトの命名規則に従う)。`index.html`は`file://`で直接開いても動作する(実測済み)。
- いずれの方式でも、テストの成否(exit code)はレポート生成の有無に関わらず正しく伝播させる。
