# Setup Matt Pocock's Skills

エンジニアリングスキル群が前提とするリポジトリ単位の設定を土台として組み立てる。

- **イシュートラッカー**: イシューがどこにあるか(デフォルトはGitHub。ローカルmarkdownも標準でサポートされている)
- **トリアージラベル**: 5つの標準トリアージロールに使われる文字列
- **ドメインドキュメント**: `CONTEXT.md`とADRがどこにあるか、そしてそれらを読む側のルール

これはプロンプト駆動のスキルであり、決定論的なスクリプトではない。探索し、見つけたものを提示し、ユーザーに確認を取り、それから書き込む。

## プロセス

### 1. 探索する

現在のリポジトリを見て、その初期状態を理解する。既に存在するものを読む。決して仮定しない。

- `git remote -v`と`.git/config`: これはGitHubリポジトリか?どのリポジトリか?
- リポジトリルートの`AGENTS.md`と`CLAUDE.md`: どちらかが存在するか?既に`## Agent skills`セクションがあるか?
- リポジトリルートの`CONTEXT.md`と`CONTEXT-MAP.md`
- `docs/adr/`および`src/*/docs/adr/`ディレクトリ
- `docs/agents/`: このスキルの過去の出力が既に存在するか?
- `.scratch/`: ローカルmarkdownのイシュートラッカー慣習が既に使われている兆候
- `triage`スキルはインストールされているか?(このスキルと並んで`triage`スキルフォルダがあるか、利用可能なスキルに`triage`が含まれているか。) これによってセクションBがそもそも実行されるかどうかが決まる。
- モノレポの兆候: `pnpm-workspace.yaml`、`package.json`内の`workspaces`フィールド、あるいは独自の`src/`を持つ`packages/*`が実際に存在するか。これらは本当に大規模なマルチパッケージリポジトリにのみ現れる。存在しない場合は単一コンテキストであり、ほとんどすべてのリポジトリがこれに該当する。

### 2. 見つけたことを提示し、質問する

存在するものと欠けているものを要約する。それからセクションを順番に進める。1セクションにつき1つの回答、それから次へ。

各セクションは推奨される回答から始めるとよい。そうすればユーザーは一言でそれを受け入れられる。選択肢が本当に分岐する場合にのみ1行の説明を添える。探索によって既に決着している場合(`triage`がインストールされていない場合のセクションB、モノレポがない場合のセクションC)はセクションを丸ごと省略する。

**セクションA: イシュートラッカー**

> 説明: 「イシュートラッカー」とは、このリポジトリのイシューがどこに存在するかを指す。`to-tickets`、`triage`、`to-spec`といったスキルはここから読み書きする。これらは`gh issue create`を呼ぶべきか、`.scratch/`配下にmarkdownファイルを書くべきか、あるいはあなたが説明する別のワークフローに従うべきかを知る必要がある。このリポジトリで実際に作業を追跡している場所を選ぶこと。

デフォルトの姿勢: これらのスキルはGitHub向けに設計されている。`git remote`がGitHubを指していればそれを提案する。`git remote`がGitLab(`gitlab.com`またはセルフホストのホスト)を指していればGitLabを提案する。それ以外の場合(あるいはユーザーがそちらを好む場合)は、以下を提示する。

- **GitHub**: イシューはリポジトリのGitHub Issuesに存在する(`gh` CLIを使用)
- **GitLab**: イシューはリポジトリのGitLab Issuesに存在する([`glab`](https://gitlab.com/gitlab-org/cli) CLIを使用)
- **ローカルmarkdown**: イシューはこのリポジトリ内の`.scratch/<feature>/`配下のファイルとして存在する(個人プロジェクトやリモートを持たないリポジトリに向く)
- **その他**(Jira、Linearなど): ユーザーにワークフローを1段落で説明してもらう。スキルはそれを自由記述の文章として記録する。

選択を`docs/agents/issue-tracker.md`に記録する。GitHubとGitLabのテンプレートには「リクエストの窓口としてのPR」フラグがあり、デフォルトは**オフ**である。オフのままにしておき、これについて特に持ち出さないこと。外部PRをトリアージキューに含めたいユーザーは、後でファイル内のフラグを切り替えられる。

**セクションB: トリアージラベルの語彙。** `triage`スキルがインストールされていない場合はこのセクションを丸ごとスキップする(探索の時点で分かっている)。インストールされていないスキルにラベルは不要だからだ。

インストールされている場合は、ちょうど1つの質問をする。

> デフォルトのトリアージラベルをそのまま使いますか?(推奨: **はい**)

デフォルトは5つの標準ロールで、各ラベル文字列はその名前と等しい: `needs-triage`、`needs-info`、`ready-for-agent`、`ready-for-human`、`wontfix`。**はい**の場合はそのまま書き込む。ユーザーが「いいえ」と答えた場合(たいていは既存のトラッカーが別の名前を使っているためで、例えば`needs-triage`の代わりに`bug:triage`)にのみ、上書き内容を集める。そうすることで`triage`は重複を作る代わりに既存のラベルを適用できる。

**セクションC: ドメインドキュメント。** デフォルトは**単一コンテキスト**(ルートに1つの`CONTEXT.md`と`docs/adr/`)。これはほとんどすべてのリポジトリに合うので、確認せずに書き込む。

探索でモノレポの兆候が見つかった場合にのみ**マルチコンテキスト**(コンテキストごとの`CONTEXT.md`を指すルートの`CONTEXT-MAP.md`)を提示する。その場合はどちらのレイアウトを望むか確認する。

### 3. 確認して編集する

ユーザーに以下のドラフトを見せる。

- `CLAUDE.md` / `AGENTS.md`のどちらを編集するにせよ、そこに追加する`## Agent skills`ブロック(選択ルールはステップ4を参照)
- `docs/agents/issue-tracker.md`、`docs/agents/domain.md`、`docs/agents/triage-labels.md`の内容(最後のものは`triage`がインストールされている場合のみ)

書き込む前にユーザーに編集させる。

### 4. 書き込む

**編集するファイルを選ぶ:**

- `CLAUDE.md`が存在すれば、それを編集する。
- なければ`AGENTS.md`が存在すれば、それを編集する。
- どちらも存在しなければ、どちらを作るかユーザーに尋ねる。勝手に選ばない。

`CLAUDE.md`が既に存在する場合は`AGENTS.md`を新規作成しない(逆も同様)。既に存在する方を常に編集する。

選んだファイルに既に`## Agent skills`ブロックが存在する場合は、重複を追記するのではなく、その場で内容を更新する。周囲のセクションへのユーザーの編集を上書きしないこと。

ブロック:

```markdown
## Agent skills

### Issue tracker

[イシューがどこで追跡されているかの1行要約]。`docs/agents/issue-tracker.md`を参照。

### Triage labels

[ラベル語彙の1行要約]。`docs/agents/triage-labels.md`を参照。

### Domain docs

[レイアウトの1行要約: 「single-context」または「multi-context」]。`docs/agents/domain.md`を参照。
```

`### Triage labels`サブブロックの記載、および`docs/agents/triage-labels.md`の書き込みは、`triage`がインストールされておりセクションBが実行された場合にのみ行う。そうでない場合は両方とも省略する。

それから、このスキルフォルダ内のシードテンプレートを出発点としてドキュメントファイルを書き込む。

- [issue-tracker-github.md](./issue-tracker-github.md): GitHubイシュートラッカー
- [issue-tracker-gitlab.md](./issue-tracker-gitlab.md): GitLabイシュートラッカー
- [issue-tracker-local.md](./issue-tracker-local.md): ローカルmarkdownイシュートラッカー
- [triage-labels.md](./triage-labels.md): ラベルマッピング(`triage`がインストールされている場合のみ)
- [domain.md](./domain.md): ドメインドキュメントを読む側のルール+レイアウト

「その他」のイシュートラッカーについては、ユーザーの説明をもとに`docs/agents/issue-tracker.md`をゼロから書く。

### 5. 完了

セットアップが完了したこと、そしてどのエンジニアリングスキルがこれらのファイルを読むようになるかをユーザーに伝える。`docs/agents/*.md`は後で直接編集できることに触れる。このスキルの再実行が必要になるのは、イシュートラッカーを切り替えたい場合やゼロからやり直したい場合だけである。
