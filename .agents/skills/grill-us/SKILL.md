# Grill Us

Jiraチケットを、実装に着手できる要件定義(spec.md)に変換する。

## プロセス

### 1. チケットを取得して要約する

チケットキー(またはURL)とspec.mdの出力先ディレクトリをまだ受け取っていなければ、ユーザーに尋ねる。利用できるJira連携(Atlassian MCP、jira CLIなど)でチケットを取得する。取得できなければ本文の貼り付けを頼む。

本文・コメント・リンクされたチケットから、次の4項目を要約してユーザーに提示する。

- **目的**: 何を達成したいか
- **背景**: なぜ今それが必要か
- **現状**: 今どう動いているか
- **期待動作**: 変更後どう動くべきか

チケットに書かれていない項目は推測で埋めない。コードベースで答えられる項目(主に**現状**)は手順2で調べる。それ以外の欠けている項目は質問として手順3の最初のラウンドに含める。

### 2. コードで答えられることを先に調べる

チームに聞く前に、サブエージェントを派遣してコードベースを調べる。最低限、次の観点を確認する。

- **画面**: 影響する画面・コンポーネント・導線
- **IF**: 関係するAPI・関数シグネチャ・データ構造・外部連携
- **権限**: ロールや認可の条件
- **既存テスト**: 現状の振る舞いを固定しているテスト
- **類似実装**: 参考にできる既存の実装パターン

調べた結果は「コードから判明した事実」としてファイルパス付きで提示し、チームが誤りを訂正できるようにする。コードで答えられたことは論点から外す。チームに聞くのは、コードが答えられないこと(意図、優先度、ビジネスルール、例外時の扱いなど)だけである。

### 3. 論点をインパクト順に質問するループを回す

Skillツールを「grilling」で呼び出し、その書式とラウンドの進め方に従う。ただし各ラウンドの質問は**インパクト順**(答え次第で仕様・工数・影響範囲が大きく変わるものから)に並べる。

回答から新たにコードで確認すべき事実が出てきたら、手順2と同じくサブエージェントに調べさせ、チームには聞かない。

不明瞭な点がなくなるまでラウンドを繰り返す。チームが「今は決めない」「別途確認する」と判断した論点は**未決事項**として記録し、ループからは外す。すべての論点が合意済みか未決事項になったら終了する。

確定した用語や後戻りしにくい決定があれば、Skillツールを「domain-modeling」で呼び出し、`CONTEXT.md`やADRに反映する。

### 4. spec.mdを出力する

合意した内容を次の構成でまとめる。

```markdown
# <チケットキー> <タイトル>

## 背景
## 目的
## 仕様
## 受入条件
## QA観点
## 未決事項
```

- **仕様**: 実装計画を立てられる粒度で書く。手順2で判明した画面・IF・権限など、関係する箇所はファイルパスで示す。
- **受入条件**: 必ずBDD形式(Given/When/Then)のシナリオで書く。

  ```
  Scenario: <シナリオ名>
    Given <前提条件>
    When <操作>
    Then <期待される結果>
  ```

- **QA観点**: 受入条件の外側で確認すべきこと(境界値、権限ごとの差、既存機能へのデグレ、データ移行など)を書く。
- **未決事項**: 論点、決める人、決まらないと何がブロックされるかを書く。なければ「なし」と書く。

ユーザーに提示して合意を取り、手順1で聞いた出力先に`spec.md`として書き込む。パスをユーザーに報告する。
