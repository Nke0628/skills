# コードベースアーキテクチャの改善

アーキテクチャ上の摩擦を洗い出し、**深化の機会**を提案する: 浅いモジュールを深いモジュールに変えるリファクタリングだ。目的はテスト容易性とAIナビゲーション容易性である。

このコマンドは、プロジェクトのドメインモデルに基づき、共有された設計語彙の上に構築されている:

- Skillツールを「codebase-design」で呼び出し、アーキテクチャ語彙(**module**、**interface**、**depth**、**seam**、**adapter**、**leverage**、**locality**)とその原則(削除テスト、「インターフェースはテスト対象面である」、「アダプタ1つは仮説的シーム、2つで本物」)を得る。すべての提案でこれらの用語をそのまま使い、「component」「service」「API」「boundary」などに逸れないこと。
- `CONTEXT.md`のドメイン言語は良いシームに名前を与える。`docs/adr/`のADRは、このコマンドが蒸し返すべきでない決定を記録する。

## プロセス

### 1. 探索する

**スキャンする前にスコープを決める: YAGNI。** モジュールを深化させることの見返りは、将来そのモジュールへの変更が楽になることで得られる。だからコードベースの中で最近変更された部分に重きを置く。見る前に、*どこ*を見るかを決める:

- ユーザーが方向性(モジュール、サブシステム、痛点)を指定した場合は、それに従い、以下の推測はスキップする。
- そうでなければ、コミット履歴(`git log --oneline`)をある程度遡って、コードベースのホットスポット - 何度も出てくるファイルや領域 - を見つけ、そのパスに最初に注意を向ける。変更が散在していて明確なホットスポットがない場合は、対象範囲を広げる。

まず、プロジェクトのドメイン用語集(`CONTEXT.md`)と、触れる領域にあるADRを読む。

次に、コードベースを歩き回るサブエージェントを起動する。硬直したヒューリスティックには従わず、有機的に探索し、摩擦を感じた箇所をメモする:

- 1つの概念を理解するために、多数の小さなモジュールを行き来する必要があるのはどこか?
- インターフェースが実装とほぼ同じくらい複雑な、**浅い**モジュールはどこか?
- テスト容易性のためだけに純粋関数が抽出されているが、実際のバグはそれらの呼び出され方に潜んでいる(**locality**がない)のはどこか?
- 密結合なモジュールがシームを越えて漏れ出しているのはどこか?
- コードベースのどの部分がテストされていない、あるいは現在のインターフェース経由ではテストしづらいか?

浅いと疑われるものすべてに**削除テスト**を適用する: それを削除すると複雑さが集中するのか、それとも単に移動するだけか? 「はい、集中する」が求めているシグナルだ。

### 2. 候補をHTMLレポートとして提示する

リポジトリに何も残らないよう、自己完結型のHTMLファイルをOSの一時ディレクトリに書き出す。一時ディレクトリは`$TMPDIR`から解決し、なければ`/tmp`(Windowsでは`%TEMP%`)にフォールバックし、実行のたびに新しいファイルになるよう`<tmpdir>/architecture-review-<timestamp>.html`に書き出す。ユーザーのために開き(Linuxでは`xdg-open <path>`、macOSでは`open <path>`、Windowsでは`start <path>`)、絶対パスを伝える。

レポートはレイアウトとスタイリングに**CDN経由のTailwind**を使い、グラフ/フロー/シーケンスが構造を確実に伝える図には**CDN経由のMermaid**を使う。Mermaidと手作りのCSS/SVGビジュアルを組み合わせる: 関係がグラフ状(コールグラフ、依存関係、シーケンス)のときはMermaidを、もっとエディトリアルなもの(質量図、断面図、折りたたみアニメーション)が欲しいときは手作りのdiv/SVGを使う。各候補には**ビフォー/アフターの可視化**をつける。視覚的であること。

各候補について、以下を含むカードを描画する:

- **Files**: どのファイル/モジュールが関わっているか
- **Problem**: なぜ現在のアーキテクチャが摩擦を引き起こしているか
- **Solution**: 何が変わるかの平易な説明
- **Benefits**: localityとleverageの観点からの説明、そしてテストがどう改善するか
- **Before / After diagram**: 浅さと深化を示す、並べて配置したカスタム図
- **Recommendation strength**: `Strong`、`Worth exploring`、`Speculative`のいずれかを、バッジとして描画

レポートの最後に**Top recommendation**セクションを置く: どの候補を最初に取り組むべきか、そしてその理由。

**ドメインには`CONTEXT.md`の語彙を、アーキテクチャには`/codebase-design`の語彙を使う。** `CONTEXT.md`が「Order」を定義しているなら、「FooBarHandler」でも「Orderサービス」でもなく「Order intakeモジュール」と語る。

**ADRとの矛盾**: 候補が既存のADRと矛盾する場合、そのADRを再検討するに値するほど摩擦が本物であるときにのみ表面化させる。カードの中で明確にマークすること(例: 警告コールアウトとして _「ADR-0007と矛盾するが、〜という理由で再検討する価値がある」_)。ADRが禁じている理論上のリファクタリングをすべて列挙しないこと。

HTMLの全体スキャフォールド、図のパターン、スタイリングのガイダンスについては[HTML-REPORT.md](HTML-REPORT.md)を参照。

まだインターフェースを提案しないこと。ファイルを書き出した後、ユーザーに「このうちどれを深掘りしたいか?」と尋ねる。

### 3. グリルのループ

ユーザーが候補を選んだら、Skillツールを「grilling」で呼び出し、意思決定ツリーを一緒に辿る: 制約、依存関係、深化させたモジュールの形、シームの向こう側に何があるか、どのテストが生き残るか。

決定が固まるにつれて副作用がその場で発生する。作業しながらドメインモデルを最新に保つため、Skillツールを「domain-modeling」で呼び出す:

- **`CONTEXT.md`にない概念にちなんで深化させたモジュールに名前を付ける場合は?** その用語を`CONTEXT.md`に追加する。ファイルが存在しなければ、その場で作成する。
- **会話の中で曖昧な用語を明確にした場合は?** その場で`CONTEXT.md`を更新する。
- **ユーザーが本質的な理由で候補を却下した場合は?** 「今後のアーキテクチャレビューで同じ提案が繰り返されないよう、これをADRとして記録しましょうか?」という形でADRを提案する。将来の探索者が同じ提案の再発を避けるために本当にその理由を必要とする場合にのみ提案する。一時的な理由(「今はその価値がない」)や自明な理由はスキップする。
- **深化させたモジュールの代替インターフェースを探りたい場合は?** Skillツールを「codebase-design」で呼び出し、そのdesign-it-twice並行サブエージェントパターンを使う。
