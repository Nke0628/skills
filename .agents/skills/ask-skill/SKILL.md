# Ask Skill

すべてのスキルを覚えていられるわけではないので、尋ねればいい。

**フロー**とはスキルを通る一本の道筋だ。ほとんどの道筋は1本の**メインフロー**に沿って進み、出発点は2つある。メインフローの後ろにはレビューを育てるループがつながっている。それ以外はスタンドアロンか、その下を走る語彙レイヤーだ。

## メインフロー: 要件 → 出荷

ほとんどの作業が辿るルート。

1. **出発点を選ぶ。**
   - **Jiraチケットがある** → **`/grill-us`**。チケットを要約し、コードで答えられることは先に調べ、残った論点をインパクト順にチームへ質問して、背景・目的・仕様・受入条件(BDD)・QA観点・未決事項に整理した`spec.md`を出力する。
   - **チケットのない、自分のアイデアがある** → **`/grill-with-docs`**。インタビューによってアイデアを研ぎ澄まし、学んだことを`CONTEXT.md`とADRに保持する。(作業ディレクトリがない? 代わりに`/grill-me`を使う。スタンドアロンの項で扱う。)
2. **分岐: すべての疑問を会話だけで解決できるか?** ある疑問がランタイムで動く答えを必要とする場合(状態、ビジネスロジック、実際に見てみないとわからないUI)は、プロトタイプへ寄り道する。この寄り道は両方向とも**`/handoff`**で橋渡しする(プロトタイプは独自のディレクトリに存在し、それはまさに`/handoff`の出番だ。「フェーズ境界」を参照):
   - **`/handoff`**で外へ出て、そのファイルを対象に新しいセッションを開く、
   - **`/prototype`**で使い捨てコードによってその疑問に答える、
   - 学んだことを**`/handoff`**で元のスレッドに戻し、そこから参照する。
3. **`/implement`**で構築する。同じコンテキストウィンドウのまま、`spec.md`や会話で合意した内容をテストファーストで実装し、コミット前に**`/code-review`**(共通・チーム固有ガイドラインに照らしたレビュー)を実行して締めくくる。PRやブランチを単体でレビューしたいときは**`/code-review`**単体を使う。
4. **`/test-e2e-harness`**でE2Eテストを作る。`spec.md`の受入条件(Given/When/Then)を、実際にブラウザを操作して記録した結果をもとにE2Eテストコードへ変換し、実行する。仕様書がなければコードからシナリオを抽出する。

### コンテキストの衛生管理

手順1〜3は**ひとつの途切れないコンテキストウィンドウ**の中で行う(`/implement`に入るまでコンパクトもクリアもしない)。そうすることで、grillingの推論がそのまま実装に引き継がれる。

これを制約するのは**[スマートゾーン](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**だ。モデルが依然として鋭く推論できる範囲(最先端モデルで約15万トークン)のこと。`/implement`の前にセッションがそこに近づいてきたら、劣化した状態で押し切らない。最寄りのフェーズ境界で`/compact`し、続ける(「フェーズ境界」を参照)。`/grill-us`の場合は`spec.md`がファイルとして残るので、`/clear`してから`spec.md`を渡して`/implement`を始めてもよい。

## レビューを育てるループ

- **`/improve-review-pr`**: バグ修正やレビュー指摘対応のPRをマージした直後に使う。元のPRのレビューで何が見落とされたかを突き止め、汎用的なチェック項目に抽象化して、`/code-review`のガイドライン(`team.md` / `common.md`)に承認を得てから追記する。同じ種類の見落としを`/code-review`が二度としないようにするためのものだ。

## 下を流れる語彙

- **`/domain-modeling`**: プロジェクトの*ドメイン*言語を研ぎ澄ます。曖昧な用語に異議を唱え、多義的な単語("account"が3つの役割を兼ねているなど)を解消し、後戻りしにくい決定をADRとして記録する。`/grill-with-docs`と`/grill-us`が内部でこれを駆動し、`CONTEXT.md`をきれいな用語集に保つ。プロセスではなく**言葉**そのものが問題になっているときは直接手を伸ばす。

## フェーズ境界

**フェーズ**とは、セッション内の作業のまとまりのことだ。grilling、実装、QAなど。2つのフェーズの**境界**では5つの選択肢があり、その間の選択はこのマップ全体の中で最も曖昧な決定だ。

- **継続**: その場にとどまる。コストなし、失うものなし。
- **`/clear`**: ここにあるものが次に何の役にも立たないとき、ウィンドウを空にする。
- **`/handoff`**は持ち運び可能なMarkdownファイルを書き出す。用途は狭く、**新しいハーネス**、**新しいディレクトリ**、**同僚**、あるいは**フェーズの途中**での副次タスクの分岐だけ。それが買っているのは可搬性だ。
- **サブエージェント**: 絞り込んだタスクを独自のウィンドウに送り、レポートを受け取る。
- **`/compact`**は現在のコンテキストを圧縮し、それを種に新しいセッションを始める。ツリーの最初の一手ではなく、その**デフォルト**、つまり一番下にある。

順序立てられたツリー(5つの問い、各分岐の背後にある理由、そしてなぜ一次情報源のコストが**継続**を最初に除外すべき選択肢にするのか)については[PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md)を読む。決定は境界で**行う**。フェーズの途中では、続けるか残りをサブエージェントに分割する。

## スタンドアロン

メインフローから外れているもの。

- **`/grill-me`**: `/grill-with-docs`と同じ徹底的なインタビューだが、**ステートレス**だ。ローカルには何も保存せず、`CONTEXT.md`も構築しない。**作業ディレクトリの中にいない**とき(プラン、デザイン、文章の断片など、下にリポジトリのない何かを研ぎ澄ますとき)に使う。作業ディレクトリの中にいるなら、記録を残せる`/grill-with-docs`を使う。
- **`/grilling`**はインタビューそのもののプリミティブだ。ラウンド、フロンティア、事実を集めるのはエージェントの仕事で、決めるのはあなたの仕事。`/grill-me`・`/grill-with-docs`・`/grill-us`はすべて内部でこれを実行する。ラッパーなしのインタビューがそのまま欲しいときだけ直接手を伸ばす。
- **`/prototype`**は1つのデザイン上の疑問に答える、小さな使い捨てのプログラムだ。この状態モデルはしっくりくるか、あるいはこのUIはどうあるべきか。メインフローの手順2にある寄り道だが、デザイン上の疑問を紙の上だけで解決しにくいときはいつでも手を伸ばしてよい。
- **`/resolving-merge-conflicts`**は進行中のマージやリベースのコンフリクトを、ハンクごとに扱う。行を選ぶのではなく、各側の一次情報源に遡った**意図**によって解決し、その後操作を完了させる。`--abort`は決して実行しない。すでにコンフリクトの最中にいるときに手を伸ばす。
- **`/wait-what`**は、うまく伝わらなかったメッセージに対する是正措置だ。他のどのスキルの最中でも、会話の途中で使うと、エージェントはあなたに欠けていた文脈を添えて、たった今言ったことを`CONTEXT.md`の語彙を使い、平易な言葉で言い直す。これは事後の対処法だ。grillingで早い段階に共通言語を合意しておくことが、事前の予防策になる。
