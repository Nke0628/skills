# Domain Docs

コードベースを探索する際、エンジニアリングスキルがこのリポジトリのドメインドキュメントをどう消費すべきか。

## 探索前に読むもの

- **`CONTEXT.md`**(リポジトリルート)、または
- **`CONTEXT-MAP.md`**(リポジトリルートに存在する場合): コンテキストごとに1つの`CONTEXT.md`を指す。取り組むトピックに関連するものをそれぞれ読む。
- **`docs/adr/`**: これから取り組む領域に触れるADRを読む。マルチコンテキストのリポジトリでは、コンテキスト単位の決定については`src/<context>/docs/adr/`もチェックする。

これらのファイルが存在しない場合は**黙って進む**。不在を指摘しないこと。事前に作成を提案しないこと。`/domain-modeling`スキル(`/grill-with-docs`と`/improve-codebase-architecture`から到達する)は、用語や決定が実際に解決されたときに遅延的にこれらを作成する。

## ファイル構成

単一コンテキストのリポジトリ(ほとんどのリポジトリ):

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

マルチコンテキストのリポジトリ(ルートに`CONTEXT-MAP.md`が存在する):

```
/
├── CONTEXT-MAP.md
├── docs/adr/                          ← システム全体の決定
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                  ← コンテキスト固有の決定
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

## 用語集の語彙を使う

出力がドメイン概念を名指しする場合(イシューのタイトル、リファクタ提案、仮説、テスト名において)、`CONTEXT.md`で定義されている用語を使う。用語集が明示的に避けている同義語に流れないこと。

必要な概念がまだ用語集にない場合、それはシグナルである。プロジェクトが使わない言葉を発明しているか(考え直す)、あるいは本当のギャップがあるか(`/domain-modeling`向けに書き留める)のどちらかだ。

## ADRとの矛盾を指摘する

あなたの出力が既存のADRと矛盾する場合、黙って上書きするのではなく、明示的に表面化させる。
