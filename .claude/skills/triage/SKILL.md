# Triage

プロジェクトのイシュートラッカー上のイシューを、少数のトリアージ・ロールから成る小さなステートマシンに沿って進める。

このリポジトリが外部プルリクエストをリクエストの窓口として扱っている場合（イシュートラッカー設定を参照）、トリアージはPRも対象にする。**PRはコードが付いたイシュー**であり、以下でマークした少数の差分を除き、同じロール・同じステート・同じマシンを使う。裸の `#42` は、トラッカー設定に従ってイシューかPRのどちらかに解決する。

トリアージ中にイシュートラッカーへ投稿するコメントやイシューは、必ずこの免責事項で始めなければ**ならない**。

```
> *This was generated by AI during triage.*
```

## ロール

2つの**カテゴリ**ロール:

- `bug`: 何かが壊れている
- `enhancement`: 新機能や改善

5つの**ステート**ロール:

- `needs-triage`: メンテナーによる評価待ち
- `needs-info`: 報告者からの追加情報待ち
- `ready-for-agent`: 完全に仕様化されており、AFKエージェントの着手可能
- `ready-for-human`: 人間による実装が必要
- `wontfix`: 対応しない

PRの場合、同じステートを添付されたコードに照らして読む。`ready-for-agent` はブリーフが添付されており、エージェントが次のステップを差分に対して行うべきという意味であり、`ready-for-human` は人間がマージする準備ができているという意味だ。

トリアージ済みの全イシューは、カテゴリロールとステートロールをちょうど1つずつ持つべきだ。ステートロールが矛盾している場合は、何かする前にそれを指摘してメンテナーに確認する。

これらは正規のロール名だ。イシュートラッカーで実際に使われるラベル文字列は異なる場合がある。そのマッピングは事前にあなたへ提供されているはずだ。提供されていなければ、ユーザーに `/setup-matt-pocock-skills` を実行するよう伝える。

ステート遷移: ラベルのないイシューは通常まず `needs-triage` になり、そこから `needs-info`、`ready-for-agent`、`ready-for-human`、`wontfix` のいずれかへ移る。`needs-info` は報告者が返信すると `needs-triage` へ戻る。メンテナーはいつでも上書きできる。通常と異なる遷移に気づいたら、進める前に指摘して確認する。

## 呼び出し

メンテナーは `/triage` を呼び出し、望むことを自然言語で説明する。リクエストを解釈して行動する。例:

- 「注意が必要なものを見せて」
- 「#42を見てみよう」（イシューまたはPR）
- 「#42をready-for-agentに移動」
- 「エージェントが拾えるものは何?」

## 注意が必要なものを表示する

イシュートラッカーに問い合わせ、古い順に3つのバケットを提示する。

1. **未ラベル**: 一度もトリアージされていない
2. **`needs-triage`**: 評価が進行中
3. **`needs-info` かつ前回のトリアージノート以降に報告者の動きがあった**: 再評価が必要

PRが対象範囲に含まれる場合、これらのバケットに外部PRも含め、各行に `[PR]` または `[issue]` のタグを付ける。発見の対象は*外部*PRのみである（誰が外部に該当するかはトラッカー設定が定義する）ため、コラボレーターの進行中のPRはトリアージ対象外だ。このフィルタは発見時のみに適用される。明示的に名指しされたPRは、作成者に関わらず常にトリアージされる。

件数と、項目ごとの1行サマリーを表示する。メンテナーに選ばせる。

## 特定のイシューまたはPRをトリアージする

1. **コンテキストを集める。** イシューまたはPRの全体（本文、コメント、ラベル、作成者、日付。PRの場合は差分も）を読む。既に解決済みの質問を再度尋ねないよう、過去のトリアージノートがあれば解析する。プロジェクトのドメイン用語集を使ってコードベースを探索し、該当領域のADRを尊重する。コードベースに対して2つのチェックを行う: (a) **重複性**: リクエストされた振る舞いの既存実装を、リクエストの文言だけでなくドメイン概念で検索し、どこを見たか報告する。見つかれば、それはすでに実装済みの `wontfix` である（手順5）。(b) **過去の却下**: `.out-of-scope/*.md` を読み、このリクエストに似たものがあれば提示する。

2. **推奨する。** カテゴリとステートの推奨内容を理由とともにメンテナーに伝え、リクエストに関連するコードベースの簡潔なサマリー（すでに実装済みかどうかを含む）も伝える。指示を待つ。

3. **主張を検証する。** グリルする前に、その主張が成り立つか確認する。バグの場合は報告者の手順から再現する。PRの場合は差分が主張通りに動くか確認する: チェックアウトし、該当するテストやコマンドを実行する。結果を報告する: 確認できた（該当するコードパスとともに）、失敗した、または情報不足（`needs-info` の強いシグナル）。検証が確認できていると、エージェント向けブリーフはずっと強力になる。

4. **必要に応じてグリルする。** リクエストの肉付けが必要な場合は、Skillツールを「grilling」と「domain-modeling」の2回呼び出し、1回のやり取りごとに質問を重ねて形にし、決定が固まるたびに `CONTEXT.md`/ADRをその場で更新してドメイン用語を研ぎ澄ませていく。

5. **結果を適用する:**
   - `ready-for-agent`: エージェント向けブリーフのコメントを投稿する（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`: エージェント向けブリーフと同じ構成だが、なぜ委任できないのか（判断の必要性、外部アクセス、設計上の決定、手動テスト）を注記する。
   - `needs-info`: トリアージノートを投稿する（以下のテンプレート）。
   - `wontfix` の場合、イシューをクローズする。コメントの内容は*理由*による。
     - **すでに実装済み**: その変更はすでにコードベースに存在する。どこにあるか示す。`.out-of-scope/` には書き込ま**ない**（そのKBは*却下*されたリクエスト向けであり、構築済みのものではない）。
     - **却下（バグ）**: 丁寧な説明をした上でクローズする。
     - **却下（エンハンスメント）**: `.out-of-scope/` に書き込み、コメントからそれにリンクした上でクローズする（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`: ロールを適用する。部分的な進捗があれば任意でコメントする。

## クイックなステート上書き

メンテナーが「#42をready-for-agentに移動」と言った場合、それを信じてロールを直接適用する。これから行うこと（ロール変更、コメント、クローズ）を確認してから実行する。グリルはスキップする。グリルセッションを経ずに `ready-for-agent` へ移動する場合は、エージェント向けブリーフを書くかどうか尋ねる。

## Needs-infoテンプレート

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

グリル中に解決した内容はすべて「established so far」の下に記録し、作業が失われないようにする。質問は具体的で実行可能なものにする。「もっと情報をください」のようなものにしてはならない。

## 過去のセッションを再開する

過去のトリアージノートがイシューまたはPRに存在する場合は、それを読み、報告者が未解決の質問に答えたかどうかを確認し、続行する前に最新の状況を提示する。解決済みの質問を再度尋ねない。
