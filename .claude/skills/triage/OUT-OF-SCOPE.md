# スコープ外ナレッジベース

リポジトリ内の `.out-of-scope/` ディレクトリは、却下された機能リクエストの永続的な記録を保管する。これには2つの目的がある。

1. **組織的記憶**: なぜある機能が却下されたのか、そのイシューがクローズされたときに理由が失われないようにする
2. **重複排除**: 過去の却下に一致する新しいイシューが来たとき、このスキルが同じ議論を蒸し返す代わりに過去の決定を表示できる

## ディレクトリ構造

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

イシュー単位ではなく、**概念**単位で1ファイルとする。同じものを求める複数のイシューは1つのファイルにまとめる。

## ファイル形式

このファイルは、データベースのエントリというより短い設計文書のような、くだけた読みやすいスタイルで書くべきだ。段落・コードサンプル・具体例を使い、初めて出会う人にも理由が明確で役立つようにする。

```markdown
# Dark Mode

このプロジェクトはダークモードやユーザー向けのテーマ機能をサポートしない。

## なぜスコープ外なのか

レンダリングパイプラインは `ThemeConfig` で定義された単一のカラーパレット
を前提としている。複数テーマをサポートするには次が必要になる。

- コンポーネントツリー全体を包むテーマコンテキストプロバイダー
- コンポーネントごとのテーマ対応スタイル解決
- ユーザーのテーマ設定を保持する永続化レイヤー

これはコンテンツ制作という本プロジェクトの焦点とは合わない、大規模な
アーキテクチャ変更である。テーマ機能は、出力を組み込んだり再配布したり
する下流の利用者側の関心事である。

```ts
// 現在のThemeConfigインターフェースは実行時切り替え向けに設計されていない:
interface ThemeConfig {
  colors: ColorPalette; // single palette, resolved at build time
  fonts: FontStack;
}
```

## 過去のリクエスト

- #42: "Add dark mode support"
- #87: "Night theme for accessibility"
- #134: "Dark theme option"
```

### ファイルの命名

概念について、短く説明的なケバブケースの名前を使う: `dark-mode.md`、`plugin-system.md`、`graphql-api.md`。ディレクトリを閲覧する人がファイルを開かなくても何が却下されたのか分かるくらい、認識しやすい名前にする。

### 理由の書き方

理由は実質を伴うべきだ。「望んでいない」ではなく「なぜ」を書く。良い理由は次のようなものを参照する。

- プロジェクトのスコープや理念（「このプロジェクトはXに焦点を当てており、テーマ機能は下流の関心事である」）
- 技術的制約（「これをサポートするにはYが必要になり、それはZアーキテクチャと矛盾する」）
- 戦略的決定（「AではなくBを使うことにした。なぜなら…」）

理由は永続的であるべきだ。一時的な事情（「今は忙しすぎる」）を参照するのは避ける。それらは本当の却下ではなく、単なる先送りだ。

## `.out-of-scope/` を確認するタイミング

トリアージ中（手順1: コンテキストを集める）に、`.out-of-scope/` 内の全ファイルを読む。新しいイシューを評価する際は次を行う。

- そのリクエストが既存のスコープ外概念に一致するか確認する
- 一致はキーワードではなく概念の類似性で判断する: 「night theme」は `dark-mode.md` に一致する
- 一致があれば、メンテナーに提示する: 「これは `.out-of-scope/dark-mode.md` に似ています。以前[理由]によりこれを却下しました。今も同じお考えですか?」

メンテナーは以下のいずれかを選べる。

- **確認**: 新しいイシューは既存ファイルの「Prior requests」リストに追加され、クローズされる
- **再検討**: スコープ外ファイルが削除または更新され、イシューは通常のトリアージへ進む
- **不同意**: それらのイシューは関連しているが別物であり、通常のトリアージへ進む

## `.out-of-scope/` に書き込むタイミング

**エンハンスメント**（バグではない）が `wontfix` として*却下*されたときのみ。これはイシューと同様、エンハンスメントPRにも適用される。却下されたPRはここに記録され、同じリクエストが新しいコードとして再び現れないようにする。

すでに実装済みであることを理由に `wontfix` としてクローズされる場合は、ここには書き込ま**ない**。それは構築済みの機能であって却下された機能ではない。記録すると重複排除チェックが偽の却下で汚染されてしまう。代わりに、クローズ時のコメントでその機能がすでにどこにあるかを示す。

流れ:

1. メンテナーが機能リクエストをスコープ外と判断する
2. 一致する `.out-of-scope/` ファイルがすでにあるか確認する
3. あれば: 新しいイシューを「Prior requests」リストに追記する
4. なければ: 概念名・決定・理由・最初のリクエストを含む新しいファイルを作成する
5. 決定の説明と `.out-of-scope/` ファイルへの言及を含むコメントをイシューに投稿する
6. `wontfix` ラベルを付けてイシューをクローズする

## スコープ外ファイルの更新・削除

メンテナーが以前却下した概念について考えを変えた場合:

- `.out-of-scope/` ファイルを削除する
- このスキルは古いイシューを再オープンする必要はない。それらは歴史的記録である
- 再検討のきっかけとなった新しいイシューは通常のトリアージへ進む
