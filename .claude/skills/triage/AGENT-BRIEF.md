# エージェント向けブリーフの書き方

エージェント向けブリーフは、GitHubのイシューやPRが `ready-for-agent` に移行するときに投稿される構造化コメントだ。これはAFKエージェントが作業のよりどころとする権威ある仕様である。元の本文と議論は文脈であり、エージェント向けブリーフは契約書だ。

ブリーフは**エージェントが何をすべきか**を述べるものであり、両方の面に及ぶ。イシューの場合はゼロから変更を構築すること、PRの場合は*既存の差分に対して*何が残っているか（仕上げ、ギャップの解消、レビュー指摘への対応）を意味する。原則はどちらも同じであり、以下のPRの例で違いを示す。

## 原則

### 精密さより耐久性

イシューは何日も何週間も `ready-for-agent` のまま置かれることがある。その間にコードベースは変化する。ファイルが名前変更・移動・リファクタリングされても有用であり続けるようにブリーフを書く。

- インターフェース・型・振る舞いの契約を記述する**こと**
- エージェントが探すべき、あるいは変更すべき具体的な型・関数シグネチャ・設定の形を名指しする**こと**
- ファイルパスを参照し**ない**こと: すぐに古くなる
- 行番号を参照し**ない**こと
- 現在の実装構造が変わらないと仮定し**ない**こと

### 手続き的ではなく振る舞い的に

システムが**何を**すべきかを記述し、**どう**実装するかは記述しない。エージェントはコードベースを改めて探索し、自ら実装上の決定を下す。

- **良い例:** 「`SkillConfig` 型は、`CronExpression` 型の任意フィールド `schedule` を受け付けるべきである」
- **悪い例:** 「src/types/skill.ts を開き、42行目にscheduleフィールドを追加する」
- **良い例:** 「ユーザーが引数なしで `/triage` を実行したとき、注意が必要なイシューのサマリーが表示されるべきである」
- **悪い例:** 「メインハンドラー関数にswitch文を追加する」

### 完全な受け入れ基準

エージェントは、いつ完了したかを知る必要がある。すべてのエージェント向けブリーフには、具体的で検証可能な受け入れ基準がなければならない。各基準は独立して検証可能であるべきだ。

- **良い例:** 「`gh issue list --label needs-triage` を実行すると、初期分類を通過したイシューが返される」
- **悪い例:** 「トリアージが正しく動作すること」

### 明示的なスコープ境界

スコープ外であるものを明記する。これにより、エージェントが過剰に作り込んだり、隣接する機能について勝手な仮定をしたりするのを防ぐ。

## テンプレート

```markdown
## エージェントブリーフ

**カテゴリ:** バグ / エンハンスメント
**概要:** 何を行う必要があるかの一行説明

**現在の振る舞い:**
現在どうなっているかを説明する。バグの場合はこれが壊れている振る舞いである。
エンハンスメントの場合はこれが機能のベースとなる現状である。

**望ましい振る舞い:**
エージェントの作業が完了した後にどうなるべきかを説明する。
エッジケースやエラー条件について具体的に書く。

**主要なインターフェース:**
- `TypeName`: 何をなぜ変更する必要があるか
- `functionName()` の戻り値の型: 現在何を返しており、何を返すべきか
- 設定の形: 必要な新しい設定オプションがあれば

**受け入れ基準:**
- [ ] 具体的で検証可能な基準1
- [ ] 具体的で検証可能な基準2
- [ ] 具体的で検証可能な基準3

**スコープ外:**
- このイシューで変更・対応してはならないもの
- 関連しているように見えるが別物である隣接機能
```

## 例

### 良いエージェント向けブリーフ（バグ）

```markdown
## エージェントブリーフ

**カテゴリ:** bug
**概要:** スキルの説明文の切り詰めが単語の途中で行われ、壊れた出力を生んでいる

**現在の振る舞い:**
スキルの説明が1024文字を超えると、単語の境界に関わらずちょうど1024文字で
切り詰められる。これにより、説明が単語の途中で終わってしまう
（例: "Use when the user wants to confi"）。

**望ましい振る舞い:**
切り詰めは1024文字より前の最後の単語境界で行われ、切り詰めを示すために
"..." を追加すべきである。

**主要なインターフェース:**
- `SkillMetadata` 型の `description` フィールド: 型自体の変更は不要だが、
  それを埋めるバリデーション/処理ロジックが単語境界を尊重する必要がある
- SKILL.mdのフロントマターを読んで説明を抽出するあらゆる関数

**受け入れ基準:**
- [ ] 1024文字未満の説明は変更されない
- [ ] 1024文字を超える説明は1024文字より前の最後の単語境界で切り詰められる
- [ ] 切り詰められた説明は "..." で終わる
- [ ] "..." を含めた合計の長さが1024文字を超えない

**スコープ外:**
- 1024文字の上限自体を変更すること
- 複数行の説明サポート
```

### 良いエージェント向けブリーフ（エンハンスメント）

```markdown
## エージェントブリーフ

**カテゴリ:** enhancement
**概要:** 却下された機能リクエストを追跡するための `.out-of-scope/` ディレクトリサポートを追加する

**現在の振る舞い:**
機能リクエストが却下されると、イシューは `wontfix` ラベルとコメントで
クローズされる。決定や理由の永続的な記録は存在しない。将来似たような
リクエストが来た場合、メンテナーは過去の議論を思い出すか検索する必要が
ある。

**望ましい振る舞い:**
却下された機能リクエストは、決定・理由・その機能をリクエストした全イシュー
へのリンクを記録する `.out-of-scope/<concept>.md` ファイルに文書化される
べきである。新しいイシューをトリアージする際は、これらのファイルとの一致
を確認すべきである。

**主要なインターフェース:**
- `.out-of-scope/` 内のMarkdownファイル形式: 各ファイルは `# Concept Name`
  見出し、`**Decision:**` 行、`**Reason:**` 行、イシューへのリンクを含む
  `**Prior requests:**` リストを持つべきである
- トリアージのワークフローは、`.out-of-scope/*.md` ファイルすべてを早期に
  読み込み、概念の類似性で新規イシューと照合すべきである

**受け入れ基準:**
- [ ] 機能をwontfixとしてクローズすると、`.out-of-scope/` 内にファイルが
      作成/更新される
- [ ] そのファイルには決定・理由・クローズしたイシューへのリンクが含まれる
- [ ] 一致する `.out-of-scope/` ファイルがすでに存在する場合、重複を作らず
      その「Prior requests」リストに新しいイシューが追記される
- [ ] トリアージ中、既存の `.out-of-scope/` ファイルが確認され、新しい
      イシューが過去の却下と一致した場合に提示される

**スコープ外:**
- 自動マッチング（一致の確認は人間が行う）
- 過去に却下された機能の再オープン
- バグ報告（`.out-of-scope/` に入るのはエンハンスメントの却下のみ）
```

### 良いエージェント向けブリーフ（PR）

PRの場合、「現在の振る舞い」は差分の現状を記述し、ブリーフはゼロから構築するのではなく、それを仕上げるか修正するようエージェントに求める。

```markdown
## エージェントブリーフ

**カテゴリ:** enhancement
**概要:** `triage list` のコントリビューターによる `--json` 出力フラグを仕上げる

**現在の振る舞い:**
このPRは、イシュー一覧をJSONにシリアライズする `--json` フラグを追加する。
正常系は動作しており、差分はプロジェクトのコマンド構造と一致している。
2つのギャップが残っている: エラーが依然として（JSONではなく）人間向けの
テキストとして出力されること、新しいフラグにテストカバレッジがないこと。

**望ましい振る舞い:**
`--json` 指定時は、（エラーを含む）すべての出力がstdoutに整形式のJSONと
して出力され、コマンドの終了コードは変わらない。フラグがない場合の既存の
人間可読な出力はそのまま保たれる。

**主要なインターフェース:**
- コマンドのエラー経路は、`--json` の下でプレーンテキストのエラーの代わり
  に `{ "error": string }` を出力すべきである
- PRがすでに追加した既存のシリアライザーを再利用する。2つ目を導入しない

**受け入れ基準:**
- [ ] `triage list --json` は成功時・エラー時の両方で有効なJSONを出力する
- [ ] 終了コードは非JSON版のコマンドと一致する
- [ ] `--json` の成功時の出力と、エラーケース1件をカバーするテストがある
- [ ] デフォルト（非JSON）の出力はバイト単位で変わらない

**スコープ外:**
- 他のコマンドへの `--json` の追加
- PRがすでに定義した成功ペイロードのJSON形状を変更すること
```

### 悪いエージェント向けブリーフ

```markdown
## エージェントブリーフ

**概要:** トリアージのバグを直す

**やるべきこと:**
トリアージまわりが壊れている。メインファイルを見て直してほしい。
150行目あたりの関数に問題がある。

**変更するファイル:**
- src/triage/handler.ts (150行目)
- src/types.ts (42行目)
```

これが悪い理由:
- カテゴリがない
- 説明が曖昧（「トリアージまわりが壊れている」）
- すぐに古くなるファイルパスや行番号を参照している
- 受け入れ基準がない
- スコープ境界がない
- 現在の振る舞いと望ましい振る舞いの説明がない
