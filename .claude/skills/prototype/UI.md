# UI Prototype

単一のルート上に、フローティングのボトムバーから切り替えられる**根本的に異なる複数のUIバリエーション**を生成する。ユーザーはブラウザ上でバリアントを切り替え、どれか一つを選ぶ(あるいは各バリアントから良い部分をつまみ食いする)。そして残りは捨てる。

疑問が見た目ではなくロジック/状態に関するものであれば、この分岐は間違いだ。[LOGIC.md](LOGIC.md)を使うこと。

## 二つの下位形態: 下位形態Aを強く優先する

UIプロトタイプは、**アプリの残りの部分と隣接している**ときの方がはるかに判断しやすい。実際のヘッダー、実際のサイドバー、実際のデータ、実際の密度。孤立した使い捨てルートは真空状態であり、どのバリアントも単独で見れば良さそうに見えてしまう。バリアントを配置できそうな既存ページがあるときは常に下位形態Aをデフォルトとする。プロトタイプが本当にどこにも近い居場所を持たない場合にのみ、下位形態Bに頼ること。

### 下位形態A: 既存ページへの調整(推奨)

ルートは既に存在している。バリアントは`?variant=`というURL検索パラメータで制御され、**同一ルート上に**レンダリングされる。既存のデータ取得、パラメータ、認証はすべてそのまま残る。レンダリングのみが切り替わる。特別な理由がない限り、これをデフォルトとして選ぶこと。

プロトタイプ対象がまだページを持っていないが、*自然にどこかのページの中に収まる*もの(ダッシュボードの新しいセクション、設定画面の新しいカード、既存フローの新しいステップ)である場合も、それは依然として下位形態Aである。バリアントをホストページの中にマウントすること。

### 下位形態B: 新しいページ(最終手段)

プロトタイプ対象に本当に収まる既存ページが存在しない場合(例: まったく新しいトップレベルの画面や、どこにも自然に埋め込めないフロー)にのみ使う。

プロジェクトが既に持っているルーティング規約に従って**使い捨てルート**を作成する。新しいトップレベル構造を発明しないこと。一目でプロトタイプだとわかるように命名する(例: パスまたはファイル名に`prototype`という単語を含める)。同じ`?variant=`パターンを使う。

下位形態Bに踏み切る前に、本当に埋め込めそうな既存ページがないかを確認すること。空のルートは、中身のあるルートなら露呈するはずの設計上の問題を隠してしまう。

どちらの下位形態でも、フローティングのボトムバーは同一である。

## プロセス

### 1. 疑問を明記し、Nを決める

デフォルトは**3バリアント**。5を超えると根本的に異なるとは言えなくなり、ノイズになり始めるので、そこを上限とする。

プロトタイプの場所か、ファイル冒頭のコメントとして、計画を一行で書く。

> 「設定ページの3バリアント、`?variant=`で切り替え可能、既存の`/settings`ルート上。」

これはユーザーが押し戻すためにここにいる場合もそうでない場合も機能する。

### 2. 根本的に異なるバリアントを生成する

各バリアントをドラフトする。それぞれを以下の基準に照らして作る。

- ページの目的とアクセス可能なデータ。
- プロジェクトのコンポーネントライブラリ/スタイリングシステム(TailwindCSS、shadcn、MUI、プレーンCSSなど何でも)。
- 明確にエクスポートされたコンポーネント名、例: `VariantA`、`VariantB`、`VariantC`。

バリアントは**構造的に異なって**いなければならない: 異なるレイアウト、異なる情報階層、異なる主要アフォーダンス。単に色が違うだけでは足りない。三つのわずかに調整されたカードグリッドはUIプロトタイプではなく壁紙である。二つのドラフトが似すぎている場合は、片方を明示的な「カードグリッドを使うな」という指示のもとで作り直すこと。

### 3. 配線する

ルート上に単一のスイッチャーコンポーネントを作成する。

```tsx
// 疑似コード。プロジェクトのフレームワークに合わせて調整すること
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

下位形態A(既存ページ)の場合: 既存のデータ取得はすべてスイッチャーより上に維持し、バリアントごとに変わるのはレンダリングされるサブツリーのみとする。

下位形態B(新規ページ)の場合: `/prototype/<name>` 配下の使い捨てルートに同じスイッチャーをマウントする。

### 4. フローティングスイッチャーを構築する

画面下部中央に固定表示される小さなバーで、三つの要素からなる。

- **左矢印**: 前のバリアントに循環する(端まで来たら折り返す)。
- **バリアントラベル**: 現在のバリアントキーを表示する。バリアントが名前をエクスポートしている場合はその名前も表示する。例: `B (Sidebar layout)`。
- **右矢印**: 次のバリアントに循環する(端まで来たら折り返す)。

挙動:

- 矢印をクリックするとURL検索パラメータが更新され(フレームワークのルーターを使う。例: Nextの`router.replace`、React Routerの`navigate`など)、バリアントが共有可能かつリロードに強い状態になる。
- キーボード: `←`と`→`矢印キーも同様に循環する。`<input>`、`<textarea>`、`[contenteditable]`にフォーカスがあるときは矢印キーを横取りしないこと。
- ページから視覚的に区別できること(例: 高コントラストのピル、控えめな影)。評価対象のデザインの一部ではないと一目でわかるように。
- 本番ビルドでは非表示にする: `process.env.NODE_ENV !== 'production'`または同等のチェックでガードし、誤ってプロトタイプがマージされてもユーザーにバーが表示されないようにする。

両方の下位形態で再利用できるよう、スイッチャーは単一の共有コンポーネントに置くこと。プロジェクト内で共有UIが置かれる場所に配置する。

### 5. 引き渡す

URL(と`?variant=`のキー)を明示する。ユーザーは都合のいいタイミングで切り替えて見る。興味深いフィードバックは大抵**「Bのヘッダーとcのサイドバーが欲しい」**というもので、それこそが本当に欲しいデザインである。

### 6. 答えを記録し、後片付けする

あるバリアントが勝者となったら、答え(どのバリアントがなぜ選ばれたか)を記録し、続いて[SKILL](SKILL.md)が説明する方法でプロトタイプを記録する。勝者を実コードに取り込み、残りはmainではなく使い捨てブランチに移す。

- **下位形態A**: 勝者を既存ページに取り込み、負けたバリアントとスイッチャーをmainから削除する。
- **下位形態B**: 勝者のバリアントを実際のルートに昇格させ、使い捨てルートとスイッチャーをmainから削除する。

バリアントの全体集合は一次資料であるため、使い捨てブランチに残す(ゴミ箱ではない)。バリアントコンポーネントとスイッチャーをmainブランチに残しておくと急速に腐り、次に読む人を混乱させるからだ。

## アンチパターン

- **色やコピーだけが違うバリアント。** それは調整であってプロトタイプではない。本物のバリアントは構造について意見が分かれる。
- **バリアント間でコードを共有しすぎる。** 共有の`<Header>`は問題ないが、共有の`<Layout>`は目的を損なう。各バリアントはレイアウトを自由に捨てられるべきだ。
- **バリアントを実際のミューテーションに配線する。** 読み取り専用のプロトタイプは問題ない。バリアントがミューテーションを必要とする場合はスタブを指すこと。疑問は「これはどんな見た目になるべきか」であって「バックエンドは動くか」ではない。
- **プロトタイプを直接本番に昇格させる。** バリアントのコードはプロトタイプの制約(テストなし、最小限のエラーハンドリング)のもとで書かれている。実コードに取り込むときはきちんと書き直すこと。
