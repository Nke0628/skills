# Codebase Design

**深いモジュール**を設計する: 小さなインターフェースの裏に大量の振る舞いを持たせ、それをきれいなシームに配置し、そのインターフェースを通してテスト可能にする。コードが設計・再構築されるあらゆる場面でこの言葉とこれらの原則を使う。狙うのは、呼び出し元にとってのレバレッジ、保守する人にとってのlocality、そして誰にとってもテスト可能性だ。

## 用語集

これらの用語を正確に使う。「コンポーネント」「サービス」「API」「境界」などに置き換えない。一貫した言葉を使うこと自体が要点だ。

**Module(モジュール)**: インターフェースと実装を持つあらゆるもの。意図的にスケールを問わない: 関数、クラス、パッケージ、あるいは複数の層にまたがるスライスでもよい。_Avoid_: unit、component、service。

**Interface(インターフェース)**: 呼び出し元がそのモジュールを正しく使うために知っておくべきすべてのこと。型シグネチャだけでなく、不変条件、順序制約、エラーモード、必要な設定、パフォーマンス特性も含む。_Avoid_: API、signature(狭すぎる。型レベルの表面だけを指してしまう)。

**Implementation(実装)**: モジュールの中身、そのコード本体。**Adapter**とは区別する: あるものは、小さなアダプターに大きな実装を持たせることも(Postgresのリポジトリ)、大きなアダプターに小さな実装を持たせることも(インメモリのフェイク)できる。シームが話題であれば「adapter」を使い、それ以外は「implementation」を使う。

**Depth(深さ)**: インターフェースでのレバレッジ。呼び出し元(あるいはテスト)が、学ぶ必要のあるインターフェースの単位あたりでどれだけの振る舞いを行使できるか。大量の振る舞いが小さなインターフェースの裏にあるとき、モジュールは**deep(深い)**であり、インターフェースが実装とほぼ同じくらい複雑なとき**shallow(浅い)**である。

**Seam(シーム)** _(Michael Feathers)_: その場所を編集せずに振る舞いを変えられる場所のこと。モジュールのインターフェースが存在する*場所*。シームをどこに置くかは、その裏に何を置くかとは別の設計判断である。_Avoid_: boundary(DDDのbounded contextと意味が重なりすぎる)。

**Adapter(アダプター)**: シームでインターフェースを満たす具体的なもの。_役割_(どの枠を埋めるか)を表し、_中身_(何が入っているか)は表さない。

**Leverage(レバレッジ)**: 深さから呼び出し元が得るもの。学ぶインターフェースの単位あたりで得られる能力が大きいこと。1つの実装がN個の呼び出し箇所とM個のテストにわたって元を取る。

**Locality(局所性)**: 深さから保守する人が得るもの。変更、バグ、知識、検証が、呼び出し元全体に散らばるのではなく、1か所に集中すること。一度直せば、どこでも直る。

## 深い vs 浅い

**深いモジュール** = 小さなインターフェース + 多くの実装:

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**浅いモジュール** = 大きなインターフェース + わずかな実装(避ける):

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

インターフェースを設計するとき、次を問う:

- メソッドの数を減らせないか?
- パラメータを単純化できないか?
- もっと多くの複雑さを内側に隠せないか?

## 原則

- **深さはインターフェースの性質であり、実装の性質ではない。** 深いモジュールは、内部的には小さくモック可能で差し替え可能な部品で構成されていてよい。それらはインターフェースの一部ではないだけだ。モジュールは、外部インターフェースにある**外部シーム**に加えて、実装に固有で自身のテストが使う**内部シーム**を持つことができる。
- **削除テスト。** そのモジュールを削除したと想像する。複雑さが消え去るなら、それは単なるパススルーだった。複雑さがN個の呼び出し元にまたがって再び現れるなら、それは存在意義があった。
- **インターフェースがテストの表面である。** 呼び出し元とテストは同じシームを横切る。インターフェースの*先*をテストしたいなら、そのモジュールの形はおそらく間違っている。
- **アダプターが1つならそれは仮説的なシーム。2つならそれは本物のシームだ。** 実際に何かがそこをまたいで変化しない限り、シームを導入しない。

## テスト可能性のための設計

良いインターフェースはテストを自然にする:

1. **依存関係は受け取るものであって、作り出すものではない。**

   ```typescript
   // テストしやすい
   function processOrder(order, paymentGateway) {}

   // テストしにくい
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **結果を返すのであって、副作用を起こすのではない。**

   ```typescript
   // テストしやすい
   function calculateDiscount(cart): Discount {}

   // テストしにくい
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小さな表面積。** メソッドが少なければテストも少なくて済む。パラメータが少なければテストのセットアップも単純になる。

## 関係性

- **Module**は正確に1つの**Interface**(呼び出し元とテストに提示する表面)を持つ。
- **Depth**は**Module**の性質であり、その**Interface**を基準に測られる。
- **Seam**は**Module**の**Interface**が存在する場所である。
- **Adapter**は**Seam**に位置し、**Interface**を満たす。
- **Depth**は呼び出し元に**Leverage**を、保守する人に**Locality**を生み出す。

## 却下したフレーミング

- **実装行数とインターフェース行数の比としてのdepth**(Ousterhout): 実装を水増しすることに報酬を与えてしまう。代わりにdepth-as-leverage(レバレッジとしての深さ)を使う。
- **「interface」をTypeScriptの`interface`キーワードやクラスのpublicメソッドとすること**: 狭すぎる。ここでのinterfaceは、呼び出し元が知るべきあらゆる事実を含む。
- **「Boundary」**: DDDのbounded contextと意味が重なりすぎる。**seam**か**interface**と言うこと。
