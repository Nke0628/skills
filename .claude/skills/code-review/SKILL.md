# Code Review

変更内容を分析し、関連するガイドラインを読み込んでレビューする。コードは修正しない。

## ガイドライン

| ファイル | 内容 | 読み込み |
|---|---|---|
| [guidelines/common.md](guidelines/common.md) | 技術を問わない横断観点 | 必ず読む |
| [guidelines/team.md](guidelines/team.md) | チームの技術スタック・規約に固有の観点 | 変更ファイルに関係するセクションだけ適用する |

lintや型チェックなど、ツールが強制しているものは指摘しない。

## 指摘のラベル

- `MUST`: 明確な不具合・違反。修正が必要。
- `IMO`: 判断の余地がある指摘。検討に値する。
- `NITS`: 動作に影響しない些細な指摘。
- `Q`: 意図や前提が読み取れず、著者に確認したい箇所。

## プロセス

### 1. 対象を確定する

引数がPR番号かURLなら**PRモード**、ブランチ名やコミットなら**ローカルモード**で進める。指定がなければ尋ねる。

- **PRモード**: GitHub MCP(なければ`gh pr view <番号> --json title,body,baseRefName,headRefName,url`)で、タイトル・説明文・ベースブランチ・ヘッドブランチを確認する。説明文やリンクされたissue・仕様書があれば、仕様の出所として控える。
- **ローカルモード**: 比較元を`<base>`として、`git rev-parse <base>`で解決できることを確認する。

### 2. レビュー用ワークツリーを用意する

PRモードでは、作業中のツリーを汚さないようワークツリーを作る。

```bash
git fetch origin <ヘッドブランチ> <ベースブランチ>
git worktree add ../review-<PR番号> origin/<ヘッドブランチ>
cd ../review-<PR番号>
```

ローカルモードでは現在のツリーをそのまま使う。

### 3. 変更ファイルを把握し、ガイドラインを読む

```bash
git diff --name-only <base>...HEAD
```

PRモードの`<base>`は`origin/<ベースブランチ>`。差分が空なら、ここで止めて報告する。

変更ファイルを見て、`team.md`のどのセクションを適用するかを決める。読む前に「どのセクションを適用し、なぜ他を外したか」を1行で述べる。迷ったら適用する側に倒す。

### 4. 影響範囲を調査する

> この手順は省略しない。変更ファイルだけを見てレビューを始めてはならない。

変更が影響しうる既存コードを能動的に調べる。範囲が広ければサブエージェントに分担させる。

- 変更されたクラス・関数・モジュールの**呼び出し元**
- 変更されたテーブル・スキーマを参照する**他のクエリ・モデル・インデックス**
- 変更されたAPIを利用する**フロントエンドや他のサービス**
- 変更によって**通らなくなりうる既存テスト**
- 同じロジックの**重複実装**

結果を次の形式で整理してから先へ進む。

```
【影響範囲サマリー】
- 直接影響: (変更されたファイル)
- 間接影響: (呼び出し元・依存先として確認したファイル)
- 影響なしと確認済み: (念のため確認したが問題なかったファイル)
```

### 5. 2サイクルでレビューする

1. **洗い出し**: ガイドライン、影響範囲サマリー、仕様の出所(あれば)に照らして、気になった点を網羅的にリストアップする。
2. **厳選**: 各候補について、本当に修正すべきか、好みの問題ではないか、重要度は高いかを批判的に検証する。実際にどう壊れるかを具体的に説明できない不具合指摘は落とすか`Q`に下げる。

指摘は変更された行にだけ付ける。感想や称賛など、指摘でないコメントは書かない。既存コードや外部資料が参考になる場合は、パーマリンク(コミットSHA付きURL)を添える。

### 6. 指摘を出力する

2サイクル目が終わってからまとめて出力する。各指摘は`[LABEL] path/to/file:line — 内容`の形にする。

- **PRモード**: pending review を作成し、各指摘を該当行にインラインコメントとして追加する。各コメントの先頭に`[AI]`の行を付ける。
  - GitHub MCPがあれば`mcp__github__pull_request_review_write`でpending reviewを作り、`mcp__github__add_comment_to_pending_review`で指摘を追加する。
  - なければ`gh api repos/{owner}/{repo}/pulls/<番号>/reviews`に、`event`を指定せず`comments`配列(`path`、`line`、`side: "RIGHT"`、`body`)を付けてPOSTする。`event`を省くとpendingで作成される。
  - **submitはしない。** 提出するかどうかはユーザーが決める。
- **ローカルモード**: 指摘をラベル順(`MUST`→`IMO`→`NITS`→`Q`)に並べてユーザーに報告する。

### 7. 後片付け

PRモードで作ったワークツリーを削除する。

```bash
cd -
git worktree remove ../review-<PR番号>
```

## 完了報告

最後に、次の2点を簡潔に報告する。

1. ラベルごとの指摘数と総合評価。指摘以外の観点(設計の別案など、水平思考での改善余地)があればここで触れる。
2. 今回のレビューを通じて、`guidelines/common.md`や`guidelines/team.md`に追加したほうがよい観点があれば、その案。
