修正PR(バグ修正やレビュー後の指摘対応のPR)を分析し、なぜ元のPRのレビューでその問題が見落とされたかを突き止め、汎用的なチェックパターンに抽象化して**このリポジトリの**`CODING_STANDARDS.md`に蓄積する。目的は、同じ種類の見落としを`/code-review`が二度としないようにすることだ。

学習したパターンはこのリポジトリ内のファイルにのみ書き込む。共有スキルである`/code-review`自体(複数プロジェクトで共有される定義)は変更しない。そちらを変更すると全プロジェクトのレビュー挙動に影響するため、このコマンドの範囲外とする。

## プロセス

### 1. 修正PRを取得する

`gh pr view <PR番号> --json title,body,url`および`gh pr diff <PR番号>`で、引数に渡された修正PRのタイトル・本文・差分を取得する。引数がPR番号でなくURLなら、そこから番号を抽出する。

### 2. 元PRを特定する

修正PRの本文から、対応した元のPRへの参照を探す(`Fixes #123`、`Follow-up to #123`、本文中のPR/issueリンクなど)。見つかれば`gh pr view`と`gh pr diff`でその内容も取得する。見つからなければユーザーに尋ねる。それでも不明なら、元PRなしで手順3に進む(修正PRの差分だけから見落としパターンを推定する)。

### 3. 見落としの理由を分析する

元PRの差分と修正PRの差分を突き合わせ、次を突き止める:

- 元PRのどのコード(ファイル・ハンク)が問題を含んでいたか
- それは`/code-review`のStandards軸(文書化された標準 + 6つの汎用的観点のベースライン)とSpec軸のどちらが拾うべきものだったか
- なぜそのレビューで見落とされたのか(6つの観点のベースラインに含まれていない、リポジトリ固有の文脈が必要、パターンが一目では気づきにくい、など)

元PRが不明な場合は、修正PRの差分自体から「何が壊れていて、何を直したか」を読み取り、同じ推論を行う。

### 4. 汎用チェックパターンに抽象化する

個別の修正を、再利用可能なチェック項目に変換する。各項目は「*何を見るか* → *どう指摘するか*」の形にする(`code-review/SKILL.md`の観点記述と同じ形式)。次の3つに分類する:

- **リポジトリ固有**: このプロジェクトのアーキテクチャ・規約・ドメインに依存する見落とし(例: 「このリポジトリでは`X`の変更時は必ず`Y`も更新する必要があるが、レビューではそれを見落としがちだ」)。
- **汎用**: どのリポジトリにも当てはまる一般的な見落とし。プロジェクトの`CODING_STANDARDS.md`には追加するが、あわせて「これは共有の`/code-review`スキルにある6つの汎用的観点のベースラインへの追加候補にもなり得る」とユーザーに伝える。共有スキルを実際に変更するかどうかはユーザーの判断に委ね、このコマンドが自動で行うことはない。
- **既存強化**: すでに文書化されている項目と本質的に同じだが、この修正PRのケースでは表現が曖昧で拾いきれなかったもの。新規追加ではなく、既存の記述を強化する文言修正として扱う。

### 5. 重複を確認する

`CODING_STANDARDS.md`(なければ`CONTRIBUTING.md`など、`/code-review`のステップ3と同じ探索順)を読み、類似のチェックがすでに存在しないか確認する。既存強化に分類したものは、ここで該当箇所を特定する。

### 6. 承認を得てから更新する

提案するチェック項目を分類ごとに一覧表示し、`CODING_STANDARDS.md`への実際の追記案(diffの形)をユーザーに提示する。**ユーザーが承認するまでファイルを書き換えない。** 承認後、`CODING_STANDARDS.md`の「## AIレビューが学習したパターン」セクション(なければ新規作成)に追記し、変更点のサマリーを表示する。

`CODING_STANDARDS.md`自体が存在しない場合は、このセクションだけを持つファイルとして新規作成してよいかユーザーに確認してから作成する。

## 書式

`CODING_STANDARDS.md`内のセクション構成:

```markdown
## AIレビューが学習したパターン

### リポジトリ固有

- **<チェック名>**: <何を見るか> → <どう指摘するか>(#<修正PR番号>より)

### 汎用

- **<チェック名>**: <何を見るか> → <どう指摘するか>(#<修正PR番号>より)
```

各項目には、それを生んだ修正PR番号を出典として残す。後で「なぜこのチェックがあるのか」を追跡できるようにするためだ。
