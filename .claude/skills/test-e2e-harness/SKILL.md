# Test E2E Harness

BDDシナリオを実際に動くE2Eテストへ変換するパイプラインである: **仕様 → YAML → ブラウザ記録 → E2Eコード → 実行**。4つのフェーズは順に依存する。前のフェーズの出力が次のフェーズの入力になるため、フェーズを飛ばしたり並べ替えたりしない。

このパイプラインが必要な理由は、BDDの文章(「ログインボタンをクリックする」)と実際のDOM操作(セレクタ、待機、アサーション)の間に距離があるからだ。距離を埋める方法は推測ではなく**実際にブラウザを操作して確かめること**である。フェーズ2(記録)を飛ばしてBDDから直接コードを生成すると、存在しないセレクタや誤った前提に基づいた壊れやすいテストができる。

## フェーズ1: BDDをYAMLに変換

1. 仕様書を探す。`docs/`、`specs/`、`*.feature`(Gherkin)、issueトラッカー、PRの説明など、プロジェクトがBDDシナリオを書いていそうな場所を確認する。
2. 見つかった場合: Given/When/Thenをそのまま[YAML-SCHEMA.md](YAML-SCHEMA.md)の形式に変換する。文言を言い換えたりシナリオを付け足したりしない。仕様書の言葉をそのまま使う。
3. 見つからない場合: 対象機能のコード(ルーティング、フォーム、UIコンポーネント、既存の統合/E2Eテスト)を読み、実際に実装されている振る舞いからBDDシナリオを逆算する。実装されていない振る舞いや「あるべき」振る舞いを創作しない。コードに存在する分岐・バリデーション・遷移だけを書く。
4. 生成したYAMLをユーザーに見せ、この仕様で問題ないか**明示的な承認を得る**。指摘があれば修正し、再度見せる。承認が得られるまでフェーズ2には進まない。承認なしに進めると、後段のブラウザ操作がすべて無駄になりかねない。

このYAMLは**テスト仕様書そのもの**として管理する。キーは英語(`feature`/`scenarios`/`given`/`when`/`then`など)だが、値はすべて日本語の自然文で書き、セレクタや操作名などの実装情報は一切含めない。保存場所はプロジェクトのE2Eテストコードの近く(例: `e2e/specs/`)。`.claude/skills/`配下には置かない。詳細は[YAML-SCHEMA.md](YAML-SCHEMA.md)を参照。

完了の目安: すべてのシナリオが`given`/`when`/`then`の日本語文として書かれ、実装情報を一切含まない状態。かつ、ユーザーからこの内容で進めてよいという承認を得た状態。

## フェーズ2: ブラウザ操作して記録

フェーズ1の仕様YAMLは自然文だけで、実際のセレクタや待機条件を持たない。ここで初めてアプリを実際に動かし、各ステップを実行しながら実装情報を**別ファイル**に記録する。仕様書に実装の詳細を混ぜないためである。

1. 利用可能なブラウザ操作ツール(Playwright MCPなど、ブラウザを実際に操作・観測できるもの)を使い、対象アプリを起動または該当URLへ移動する。ローカル起動が必要な場合は`run`スキルの要領でアプリを立ち上げる。
2. 仕様YAMLの各文を順に実行する。`when`の文は操作(`navigate`/`click`/`fill`/`select`/`check`など)として記録し、`then`の文は実際の画面を確認したうえでアサーション(`assert-visible`/`assert-text`/`assert-url`など)として記録する。
3. セレクタは実際に画面上で解決できたものだけを記録する。推測したセレクタや「たぶんこれだろう」というセレクタを書かない。`data-testid` → ロール/ラベル → 可視テキストの優先順で、壊れにくいセレクタを選ぶ。
4. `then`のアサーションは、その時点で実際に画面に表示されている内容から書く。期待値を先に想像してから当てはめない。
5. 各ステップの実測結果を、仕様YAMLの文と対応づけて記録ファイルに書く。

途中で仕様と実装の食い違い(ボタンが存在しない、遷移先が違う、フェーズ1で書いたシナリオが実行不可能など)に気づいたら、その場でユーザーに報告する。黙って辻褄を合わせない。

完了の目安: すべてのステップが実際に実行され、記録ファイルに実測値が埋まっている状態。仕様YAML自体には変更が入らない。詳細は[RECORDING.md](RECORDING.md)を参照。

## フェーズ3: E2Eのコードに変換

仕様YAML(何を検証するか)と記録ファイル(どう操作するか)の2つを入力にする。

1. プロジェクトが既に使っているE2Eフレームワークを検出する(`playwright.config.*`、`cypress.config.*`、`package.json`の依存関係)。存在しなければユーザーに確認する。決め打ちしない。
2. 既存のテストの配置場所・命名規則・ヘルパー関数(ログイン処理の共通化など)の前例を踏襲する。新しい規約を発明しない。
3. フェーズ2で確定したセレクタ・操作・アサーションをそのままコードに落とす。BDDのGiven/When/Thenは、コード中のコメントまたは`test.step`のようなブロックとして残し、仕様とコードのトレーサビリティを保つ。
4. 固定時間の`sleep`は使わない。フレームワークの自動待機、または明示的な条件待ち(要素の出現、ネットワーク完了など)を使う。
5. E2Eフレームワークを新規導入する場合は、スクリーンショット・動画等を残すレポーター設定も合わせて用意する。詳細は[CODEGEN.md](CODEGEN.md)の「レポート出力」を参照。**この設定自体は初回導入時のみだが、レポートを実際に生成して共有する作業はフェーズ4でテストを実行するたび毎回行う。**

完了の目安: 生成したコードがフェーズ1のシナリオと1対1で対応し、フレームワークの型チェック/lintを通る状態。詳細は[CODEGEN.md](CODEGEN.md)を参照。

## フェーズ4: 実行

1. まず今回追加・変更したテストだけを対象を絞って実行する(例: `playwright test e2e/tests/dev.spec.ts`)。
2. 失敗した場合、フェーズ2の記録に立ち返って原因を切り分ける: 仕様の理解が誤っていたのか、セレクタが変わったのか、実装のバグなのかを区別する。原因を推測で決め打ちしない。
3. flaky(不安定)な失敗が出た場合、待機条件の不足を疑う。リトライ回数を増やして誤魔化さない。
4. 対象のテストが全て成功したら、既存のテストも含めた全体を実行し、今回の変更が他画面のテストを壊していないか回帰確認する。
5. レポートは今回の変更対象だけに絞って作る。回帰確認用の全体実行結果をそのまま使い回さない — [CODEGEN.md](CODEGEN.md)の「レポート出力」に従い、対象テストだけを指定して実行し直し(手順1と同じ絞り込み)、`docs/<チケット名>/test/report/`にコミットして共有する。**これを忘れて「完了」と報告しない。**
6. 実行結果(対象テスト・全体回帰確認それぞれの成功/失敗、失敗理由)とレポートの共有結果をユーザーに報告する。対象テストと全体回帰確認がすべて成功し、対象範囲のレポートを共有し終えるまでフェーズ4を終えたとみなさない。
