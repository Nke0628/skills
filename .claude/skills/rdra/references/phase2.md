# フェーズ2: 要件を組み立てる(Step5〜6)

目的: RDRAの要素のつながりを使い、論理的に要件を組み立てる。要件はヒアリングをまとめるのではなく、業務を理解して役に立つシステムの要件を組み立てる。

## 前提の確認

1. `rdra.py gate 1` → `rdra.py set-phase 2`(SKILL.md「判定と --force」)。
2. 00〜05 と questions.md の回答済・反映済の質問を読む。`回答` の行は確定事項として扱う。

## 作るもの

### Step5: トップダウンで要件を組み立てる(03_BUC)

1. 業務・BUC・アクティビティを見直す(変える必要があれば、変えずに質問を出す)。
2. システム化するアクティビティにUCをつなげる。UC名は「XXXをYYYする」。ざっくり素早く洗い出す。
3. UCに関わるアクターから**画面**を、関わる外部システムから**イベント**を導く。時刻起動は `タイマー:〜`。
4. UCの入出力として**情報**の列を埋める。

### Step6: 情報・状態を使って見直す(04_情報、05_状態)

1. 情報に属性(主要な項目)を書き、情報関連を書く。
2. 欠けている情報を洗い出す(UCの入出力から必要になる情報、関連を張ると必要になる情報)。
3. 見直した情報をUCにつなげ、UCが行うことを明確にする。
4. 状態遷移(遷移先・遷移UC)を書く。UCが状態を変えるなら、そのUCが状態を持つ情報を扱っているかを確認する。
5. 情報と状態モデルのコンテキストを見直す。

Step5 と Step6 は1回の phase2 の中で2〜3周する。周回ごとに `rdra.py check` を実行し、P201(UCにつながらない情報)、P202(遷移UCのない状態モデル)、P203(画面もイベントもないUC)をつぶす。つぶせないものは質問にする。

## 出典の扱い

- フェーズ2で導いた要素(UC・画面・イベント・属性・関連・遷移)は、入力や回答に明記がなければ `仮説`。
- ただし、確定した行から一意に導けるもの(例: 確定したアクティビティ「予約を申し込む」に対するUC「予約を登録する」)も、システム化の境界は人が決めるため `仮説` とする。質問は境界ごとにまとめてよい(例: 「BUC『Webで予約を受け付ける』で、システムを使うのは次の3つのアクティビティでよいか」)。

## 仕上げ

質問を作り、コミットする(メッセージ `rdra: phase2 生成`)。

## 報告

UC・画面・イベント・情報・状態遷移の数とそのうち仮説の数、優先度・高の質問の件名、`rdra.py check` の致命の残数、次にやること。
