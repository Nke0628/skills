# design: このスキルの設計の判断

---

スキルを直す人向けのメモ。実行時には読まない。手順の詳細は SKILL.md と各手順書にあり、ここでは「なぜそうしたか」だけを残す。直すときは、この意図を崩さないようにする。

| #   | 論点                       | 決めたこと                                                           | 理由                                                                                                             |
| --- | -------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 1   | 進め方                     | AIが叩き台を作り、人が調整する。推測せず質問する                     | RDRAの「LLMでたたき台、人とキャッチボールで詳細化」+ 食べログ方式                                                |
| 2   | 推測禁止と叩き台の両立     | 全行に出典ラベル。`仮説` の行には質問IDを付ける                      | RDRAの「まず全部を埋める」には面積が要る。決まっていないことを決定事項のように見せる失敗を出典ラベルで防ぐ       |
| 3   | スキルの分け方             | 1つのスキルを引数で切り替える                                        | 要素・出典・質問ルールが全フェーズ共通。フェーズ別手順は references/ に分け、必要な時だけ読み込む                |
| 4   | 調整結果の取り込み         | 反映専用の `apply`。何周でも回せる                                   | RDRAは行き来して精度を上げる手法。回答を受けて聞き返すことが重要                                                 |
| 5   | 各フェーズの成果物         | 9ステップ方式 + 要求(フェーズ1)+ 整合性チェック・重要UC(フェーズ3)   | 公式のメインの方法論。要求は「なぜ」のたどり先、チェックは完成判定に使う                                         |
| 6   | ファイル構成               | RDRAのシートに対応したファイルを、フェーズをまたいで育てる           | 「モデルごとにシートを分け、名前で関連付ける」原則。同じものを二重に持たない                                     |
| 7   | 質問の回答方法             | ローカルの questions.html → answers.json。正本は questions.md        | リポジトリで完結させ、判断の根拠を git に残す。特定アカウントの機能に依存しない                                  |
| 8   | 人の編集の検出             | git の差分。AIは `docs/rdra/` の中だけをコミットする                 | 判断の履歴が残り、検出も確実                                                                                     |
| 9   | 判定条件                   | `rdra.py gate` の機械的な条件。`--force` は事実と理由を記録          | 優先度・高の基準を機械的な条件にする。分かっていて進めたい場面にも対応する                                       |
| 10  | 観点チェックリスト         | 構造から / 立場別 / プロジェクト固有(checklist-local.md)の3層        | 根拠のある質問を作り、業務への影響の見落としを防ぎ、業務知識を蓄積する                                           |
| 11  | 入力                       | 初期要望.txt はテンプレート形式。追加資料は `docs/rdra/inputs/`      | 2階層の概要が出力の精度を上げる(ZeroOneの経験則)。議事録を取り込めるようにする                                   |
| 11a | 初期要望の作り方           | `draft` で下書きを作り、人が「採用」と指示したときだけ `adopt`       | 初期要望は出典 `要望` の元で、全体の精度を決める。AIの要約が `要望` として紛れ込まないよう、下書きと採用を分ける |
| 12  | 機械的な処理               | `scripts/rdra.py`(標準ライブラリのみ)。AIは意味の判断と質問文        | 判定と図の生成を毎回同じ結果にするため                                                                           |
| 13  | 列構成                     | `table-format.md` で固定                                             | スクリプトで読めるようにするため                                                                                 |
| 14  | 前のフェーズに戻るとき     | いつでも修正してよい。波及先は `仮説` に戻す。フェーズ番号は戻さない | 行き来を軽く保ちながら、推測による変更を防ぐ                                                                     |
| 15  | 図                         | 表から Mermaid 図を生成する(`rdra.py diagrams`)                      | 図と表のずれを原理的になくす                                                                                     |
| 16  | トレーサビリティのレビュー | 到達は `rdra.py trace`、意味は別文脈のサブエージェントが見る         | 到達は機械で見られるが、つながりが「なぜ」を本当に説明しているかは書いた本人には見えにくい                       |
