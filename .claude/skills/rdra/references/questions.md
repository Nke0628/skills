# 質問の作り方

参考: 食べログ「AIに質問させる要件定義」。AIの役割は気づきを求める質問を出すこと、人の役割は判断を下すこと。

## 書式

`docs/rdra/questions.md` に追記する。IDは `rdra.py next-qid` で取得し、連番で振る。

```markdown
### Q-012 [高] [フェーズ1] 予約のキャンセルは誰が行うか
対象: 03_BUC.md「予約を管理する」/ 仮説行: UC「予約をキャンセルする」
提案: 会員本人と店舗スタッフの両方
根拠: 要望.md に「会員が予約を変更できる」とあるがキャンセルの記述なし。店舗都合のキャンセルは一般に必要
観点: 利用者
選択肢:
  A) 提案どおり(会員+スタッフ)
  B) 会員のみ
  C) スタッフのみ
  D) その他 → ___
回答:
状態: 未回答
```

- 見出しは `### Q-NNN [高|中|低] [フェーズN] 質問文`。フェーズは質問を出したときのフェーズ。
- `提案` と `根拠` は必須。選択肢は2〜5個、最後は必ず「その他」。選択肢が成り立たない質問(名前を決める等)は選択肢なしでよい。
- `回答:` と `状態:` の行は空でも必ず書く(HTMLとスクリプトが使う)。
- 状態は `未回答` → `回答済`(answers.json を取り込んだ)→ `反映済`(成果物に反映した)。人が判定から外すときは `許容`。

## 優先度の基準(厳しめにする)

- **高:** 回答がないと次のフェーズに進めない、または後で覆ると手戻りが大きいもの。スコープ、アクターの有無、BUCの有無、情報の有無、システム化するかどうかの境界。
- **中:** つながりや名前の精度に関わるもの(どのUCがどの情報を扱うか、状態遷移の抜け、名前の揺れの統一)。
- **低:** 表現の揺れ、補足説明。

迷ったら1段低くする。「全部高」にすると仕分けの意味がなくなる。

## 量

- 1回の生成・反映で出す優先度・高は**最大10問**。超えそうなときは、手戻りの大きいものから10問を選び、残りの論点に関わる仮説の行は今回は書かない(次の apply で、回答を踏まえて書く)。高を中に格下げして数を合わせてはいけない。
- 中・低は数の上限なし。チャットでは件数だけを報告する。

## 作り方

1. 書いた仮説の行ごとに、何が確かでないかを1つの質問にする。関連する仮説が複数行にまたがるときは1つの質問にまとめ、各行の質問列に同じIDを書く。
2. `rdra.py check` の結果(構造の穴)から質問を作る。根拠には指摘のキーではなく、何が足りないかを言葉で書く(例: 「店長がどの業務にも登場しない」)。
3. 該当フェーズの `checklist-phaseN.md` の立場別の観点と、`docs/rdra/checklist-local.md` を順に当て、穴を探す。

## 良い質問

- 抽象的に聞かない。「アクターは他にいますか?」ではなく「返品の受付は店舗スタッフとコールセンターのどちらが行いますか?」
- 根拠に、資料の該当箇所の引用か、チェック結果を書く。「一般的に」だけを根拠にしない。
- 提案は、仮説の行に書いた内容と一致させる。
- 回答者が業務の言葉で答えられるようにする(RDRAの用語を回答者に求めない)。
- **行番号を書かない。** `25行目` `03_BUC.md:25` のような位置は、questions.html を読む人には分からない。表の要素は名前で示す(アクティビティ「退会する」、ルール「制度の改正の反映」)。要求・ゴールはIDに内容を添える(R-05「制度を計算に反映し、改正に追従する」)。
- **内部の記号を書かない。** チェックのキー(`P209:…`)は、提案・根拠・選択肢に書かない。
