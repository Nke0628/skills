# mock: 画面モックを作る

目的: フェーズ2で洗い出した画面・UC・情報の属性を、粗いワイヤーフレームにして関係者に見せ、「この画面で何を入力・確認するか」が業務に合っているかを確かめる。見た目やレイアウトを決めるものではない(それは要件定義のあとのUI設計で行う)。

## いつ使うか

- フェーズ2以降(03_BUC に画面、04_情報 に属性があるとき)。フェーズ1では画面がないので作らない。
- 項目(属性)が推測のときや、入力画面が多く分け方を判断しにくいときに特に効く。

## 手順

1. `rdra.py mock` を実行し、`docs/rdra/mock.html` を作る。**AIがモックに画面・項目を書き足したり、手で直したりしない。** 足りない項目は表(04_情報 の属性、03_BUC の画面・UC)を直してから作り直す。
2. 作ったモックを見て、MTGの前に気づいたことを報告する(モックには書かない)。例:
   - 入力欄が一つもない画面(属性が空、またはIDだけの情報)
   - 同じ画面に、関係の薄い操作が並んでいる
   - 一覧・削除・変更の操作がない情報(CRUDの欠け)
   報告した論点のうち表を変えるべきものは、`references/questions.md` に沿って質問にする。
3. コミットする(メッセージ `rdra: mock 生成`)。

## 生成のきまり(rdra.py が行うこと)

- 画面は 03_BUC の画面列から、BUCの行の順に並べる。同じBUCに画面が3つ以上あれば、画面の上にステップの切り替えを出す。
- UCの動詞で部品を変える。
  - 登録する・設定する・作成する・更新する → 入力フォーム。主な情報(情報列の先頭)の属性を入力欄にする。
  - 情報が「1対多」の多の側・「多対多」なら、一覧と「+追加」にする。
  - 認証する → ログインボタン(外部システムがあれば「<外部システム>でログイン」)
  - 試算する → 実行ボタン / 表示する → グラフと表 / 比較する → 2つを選んで重ねる
  - 複製する・削除する・〜に反映する → 一覧の行ごとのボタン / 退会させる → 削除される情報の警告と退会ボタン
  - 3つ以上の画面にまたがるUC(例: 比較パターンを変更する)→ 同じ入力画面を複製せず、各画面の上に「編集する対象: 現状 / <主な情報>を選ぶ」の切り替えを出す
- 属性のうち、末尾が `ID` `状態` `日時` `登録日` のものはシステムが決める項目として入力欄にしない。ただし `<他の情報>ID` は「対象の<情報>」の選択欄にする。
- 属性名から入力の形を決める(`〜額` `〜金` → 円、`〜率` `利回り` `金利` → %、`年齢` → 歳、`〜年` `期間` → 年、`種類` `区分` `続柄` など → 選択)。属性に `(A・B)` と書けば選択肢になる。
- 外部システムから取る属性は「<外部システム>から取得」と表示する。
- 運営者など管理側のアクターの画面は、上のバーの色を変える。
- PC幅とスマートフォン幅を切り替えられる。各画面にメモ欄があり、「メモをコピー」でまとめられる(ブラウザにだけ保存)。

## MTGのあと

人が「メモをコピー」でまとめたものを `docs/rdra/inputs/画面モックへのメモ_YYYYMMDD.md` に保存し、`/rdra apply` で追加資料として反映する。

## 報告

mock.html のパス、画面の数、MTG前に気づいた論点、MTG後の流れ(メモ → inputs → `/rdra apply`)を短く伝える。
