# フェーズ3: ビジネスルールで仕様化可能にする(Step7〜9)

目的: 条件とバリエーションを明示してビジネスルールを明らかにし、仕様化につなげる。要件レベルでは条件の詳細には踏み込まず、条件とバリエーションのつながり(トレーサビリティ)を管理する。

## どこまで深掘りするか

**詳細に踏み込まないことと、曖昧なままにすることは違う。** 計算式は書かない。ただし、判定に必要な材料が情報モデルにそろっているかは、要件のうちに確かめる。材料が後から足りないと分かると、情報モデルの手戻りになる。

| 要件定義(このフェーズ)で決める | 仕様化(要件定義のあと)で決める |
|---|---|
| どんなルールがあるか、どのUCで効くか | 計算式、判定の手順 |
| 何によって結果が変わるか(バリエーション・状態) | 端数の扱い、月の途中・境界の日の扱い |
| 判定に使う値(対象かどうか、率・上限額、期間・期限)が、バリエーション・情報の属性・状態のどれにあるか | 率・上限額などの具体的な数値 |
| 率・上限額のように変わる数値を、どこに持つか(固定・マスタ・パラメータ) | |

条件ごとに「このルールで結果を出すには、何が分かっていればよいか」を挙げ、表にないものを質問にする。例: 「育休の期間の給与を育休手当に置き換える」なら、対象者の判定(雇用保険に入っている働き方か)、給付率が変わる期間、上限額、育休中の社会保険料の扱い。式(賃金の67%を180日など)は書かず、率と上限を「パラメータに持つ」とだけ書く。

式や数値の詳細を残したいと言われたら、要件の表には書かず、`docs/rdra/inputs/` とは別の仕様メモとして作る。

## 前提の確認

1. `rdra.py gate 2` → `rdra.py set-phase 3`(SKILL.md「判定と --force」)。
2. 00〜05 と questions.md を読む。

### 条件を探す場所
- 01_要求 のビジネスポリシー(ほぼ必ず条件になる)
- 業務フローで分岐が起きるアクティビティ(承認・却下、在庫あり・なし)
- 状態によって可否が変わるUC(「予約済ならキャンセルできる」)
- 区分・種別で扱いが変わるところ(会員種別、商品区分、地域)

### 条件の表の扱い
- 軸の値の組合せごとに結果を1行書く(書式は `table-format.md`)。組合せの抜けは `rdra.py check` が P307 で出す。
- 説明の文章から言える結果は、その行の出典に合わせる。文章から言えない組合せは `仮説` で書き、質問にする。抜けた組合せを見つけることが、表にするいちばんの目的。
- 軸の値によって結果が変わらないときは `すべて` でまとめる。組合せが多すぎて表が読めないときは、軸の分け方(バリエーションの値のまとめ方)を見直す。

### バリエーションの扱い
- 値を列挙するだけで、詳細なルールは書かない。
- ビジネスの変化は値の追加・変更として現れることが多い。値が増えそうなものは質問で確認する(保守性に効く)。
- バリエーションは情報の属性として関わる。値を持つ情報のバリエーション列に書き、属性にも対応する項目を置く。属性がなければ、属性の追加を仮説で書く。

## 整合性チェックと重要UC

1. `rdra.py check` で全フェーズの指摘を確認する。致命と警告は、直すか質問にする。
2. `rdra.py analysis` で analysis.md を生成し、重要UC(複数コンテキスト・複数状態モデルにまたがるUC)を確認する。重要UCについて、条件・状態遷移の抜けがないかを重点的に見る。

## 仕上げ

質問を作り、`rdra.py analysis` も実行してからコミットする(メッセージ `rdra: phase3 生成`)。

## 報告

条件・バリエーションの数と仮説の数、重要UCの一覧、優先度・高の質問の件名、完成条件までの残り(`rdra.py gate done` の理由の件数)、次にやること。
