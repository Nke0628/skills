# フェーズ1: 議論のベースを作る(Step1〜4)

目的: 精度は気にせず短時間で議論のベースを作り、空中戦を避ける。スコープと登場人物について合意できる状態にする。

## 前提の確認

1. `rdra.py lint-request` を実行する。
   - 致命が出たら止まる。「すべて空」なら、初期要望.txt を書くか、inputs/ に資料があれば `/rdra draft` を案内する。「下書きの印が残っている」なら、`/rdra draft` の採用の手順を案内する。
   - `初期要望.draft.txt` があり初期要望.txt が空のときも止まり、下書きの見直しと採用を案内する。
   - 警告・情報は報告に含めて進める(空欄は質問になる)。
   その後 `docs/rdra/初期要望.txt` を読む。
2. `docs/rdra/inputs/` のファイルをすべて読む(読めない形式はその旨を報告)。
3. 00〜05 にすでに行があれば(2回目の phase1)、上書きせず、既存の行を残して不足分だけ足す。人の `回答` 行は変えない。

## 作るもの

| Step | 書く表 | 内容 |
|---|---|---|
| 1 出発点 | 00_ゴール、01_要求(ゴールID列を含む)、02_アクター、03_BUC(業務・BUC列) | 最重要要求・背景からゴールと要求を、登場人物からアクター・外部システムを、業務の概要から業務・BUCを洗い出す。要求はゴールにつなぐ |
| 2 スコープ | 03_BUC(アクティビティ・先・次・アクター・外部システム・要求ID列) | BUCごとにアクティビティを粗く並べ、先・次で流れをつなぐ(BUCをまたぐつながり・分かれ道も)。正確さより洗い出しを優先 |
| 3 情報 | 04_情報(コンテキスト・情報・説明)、03_BUC(情報列) | 業務で扱う情報をID単位で。必要そうなものは一旦出す |
| 4 状態 | 05_状態(状態モデル・状態) | 業務が認識している状態を列挙。遷移先・遷移UCは空でよい |

フェーズ1で書かない列: 03_BUC の UC・画面・イベント・条件、04_情報 の属性、情報関連、05_状態 の遷移先・遷移UC、06_条件(全体)。

## 進め方

1. **入力に書かれていることだけで埋める。** 出典は `要望` か `資料:<ファイル名>`。初期要望の業務の概要は、1階層目を業務、2階層目をBUCにする。そのうえで `model.md`「業務・BUC・アクティビティの粒度」の判断の問いと症状を当てる。粒度がずれているとき(主役の違う仕事が1つの業務に混ざる、状態を進めないBUC、途中に待ちのあるBUCなど)も、要望どおりに書いたうえで、どう分ける・まとめるかの質問を出す。
2. **入力から言えないが、ないとつながらないものを仮説で足す。** 例: アクティビティを並べると必要になる中間のアクター、情報の保管先になる外部システム。必ず質問を付ける。
3. **ゴールは1〜3件。** 最重要要求から作り、出典は `要望`。達成の判断基準が入力から言えなければ、空にして優先度・高の質問にする(例: 「何がどれだけ達成できたら成功と言えるか」)。
4. 初期要望の空欄の項目は、優先度・高の質問にする(例: 最重要要求が空 → 「このシステムで一番実現したいことは何か」)。`/rdra draft` で出したフェーズ0の質問が未回答で残っていれば、同じ論点の質問を新たに作らず、それを引き継ぐ(関係する仮説の行の質問列にそのIDを書く)。
5. コンテキストは、情報が出揃ったところで仮にまとめる(フェーズ1では仮説で構わない)。
6. `rdra.py check` の結果のうち、P101(アクティビティのないBUC)、P102(アクターのないアクティビティ)、P110(要求のないゴール)、P112(ゴールがない)は、行を足すか質問にする。
7. 質問を作る。
8. `rdra.py set-phase 1` を実行してからコミットする(フェーズ2以降での再実行なら番号は変わらない)(メッセージ `rdra: phase1 生成`)。

## 報告

- ゴール・業務・BUC・アクティビティ・アクター・情報・状態モデルの数と、そのうち仮説の数
- 優先度・高の質問の件名、中・低の件数
- 次にやること: 「`docs/rdra/questions.html` を開いて回答し保存 → MTGで決まったことは表を直接直すか inputs/ に議事録を置く → `/rdra apply`」
